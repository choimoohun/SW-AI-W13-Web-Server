# 프로젝트 운영 규칙

이 문서는 사람이 읽는 기준입니다. AI도 참고하지만, 문서의 주인은 프로젝트를
책임지는 사람입니다. 규칙 자체보다 **판단 근거가 나중에 다시 읽힐 수 있게 남기는 것**이 목적입니다.

## 1. 문서 역할

| 문서 | 역할 | 상태 기준 |
|---|---|---|
| `README.md` | 입구. 현재 구조, 실행 방법, 검증 명령 | 항상 현재 상태 |
| `eungi/REQUIREMENTS.md` | 과제 요구사항과 수용 기준. 결정 대기를 확정해서 적음 | 기준 문서 |
| `eungi/DESIGN.md` | 현재 구조, 모듈 책임, 의존·소유권·계약 | 항상 현재 상태 |
| `eungi/DECISIONS.md` | 선택지, 선택 이유, 영향, 대체 관계 | 채택/대체 이력 |
| `eungi/STEP1~10` | 단계별 문제-설계-검증 기록 | 단계 완료 후 보존 |
| `verify/VERIFICATION_LOG.md` | 실제로 실행한 명령과 결과 | 실행한 것만 기록 |
| `verify/ARCHITECTURE_REVIEW.md` | 현재 구조의 리스크와 다음 우선순위 | 구조 변경 시 갱신 |
| `verify/DESIGN_REVIEW.md` | 초기 설계 시점의 검토 기록 | 과거 기록으로 보존 |

통합 문서는 요약이고, 상세 근거는 단계 문서와 검증 로그에 둡니다. 같은 내용을
여러 문서에 복사하지 않고 링크로 연결합니다.

## 2. 상태 표기

- 문서 상단에 현재 성격을 적습니다. 예: "현재 상태", "초기 검토 기록", "당시 범위".
- 과거 기록은 지우지 않고 `당시 …`, `이후 … 완료`로 표시합니다.
- 설계 확정과 구현 완료는 다릅니다. 구현하지 않은 기능을 완료로 적지 않습니다.
- 실행하지 않은 테스트를 통과했다고 적지 않습니다. 실패와 차단도 그대로 남깁니다.

## 3. 결정 기록

이미 확정한 선택은 `eungi/DECISIONS.md`에 `D01`~`D28`로 있습니다.
새로 바뀌는 선택은 기존 행을 지우지 않고 **새 결정**으로 추가합니다.

사람이 직접 판단해야 했던 지점은 특히 흐릿하게 넘기지 않습니다.

- `D26`: HTTP/2를 C 파서로 구현하지 않고 앞단 게이트웨이에서 종료
- `D27`: 항공편 도메인은 C 안에 두고 캐시·DB·프론트만 별도 프로세스로 연결
- `D28`: 결제를 별도 프로세스/DB로 분리, 중복 방지 키를 본문에 포함
- 환불 기간과 비율: 출발 임박 구간의 정책을 사람이 확정
- 로그인 방식: 다음 단계에서 레디스 세션으로 붙이기로 방향을 정함

## 4. 코드와 검증 표기

- 코드 식별자, 파일명, 명령, API 경로는 백틱으로 감쌉니다.
- "모듈을 분리했다"는 말은 파일을 나눈 것만 뜻하지 않습니다. 의존 방향,
  소유권, 계약을 문서에 적어야 합니다.
- 테스트 결과에는 명령, 조건, 실제 출력을 함께 적습니다.
- 부하 수치는 RPS만 적지 않고 동시성·요청 수·환경을 함께 적습니다.

## 5. 에이전트와 사람의 경계

에이전트는 비교·구현·실행·기록을 도울 수 있지만, 아래는 사람이 정합니다.

- 요구사항 범위와 우선순위
- 서비스 경계와 배포 형태
- 보안/결제/환불 같은 정책
- "지금은 안 한다"와 "다음에 한다"의 구분

이 문서는 그 판단이 나중에 다시 읽힐 수 있게 두는 최소한의 틀입니다.
