# 웹서버가 푸는 중심 문제

이 문서는 프로젝트의 역사적 기원을 단정하지 않습니다.
이 프로젝트가 다루는 중심 문제는 이렇습니다.

> TCP가 주는 것은 **바이트 스트림**일 뿐인데, 클라이언트는 **요청과 응답**을 원한다.
> 이 차이를 안전하게 메우고, 여러 클라이언트가 동시에 써도 깨지지 않게 만드는 것.

여기서 갈라지는 문제들이 순서대로 생겼습니다.

| 문제 | 왜 생겼나 | 그래서 생긴 것 |
|---|---|---|
| 요청 경계가 없다 | TCP에는 메시지 끝 표시가 없음 | `CRLF`, `CRLF CRLF`, `Content-Length`, `req.consumed` |
| 파일을 그대로 보낼 수 없다 | 경로 탈출, MIME, 바이너리 손상 위험 | `realpath` 경계 검사, MIME, 청크 전송 |
| 한 클라이언트가 느리면 다 멈춘다 | 블로킹 `recv()`가 스레드를 점유 | `O_NONBLOCK`, `iomux`, 워커 풀 |
| 연결을 매번 닫으면 비싸다 | TCP 핸드셰이크 비용 | keep-alive 최대 100회, 유휴 5초 |
| 좌석을 두 명이 같은 순간에 잡는다 | 공유 상태에 동시 접근 | 항공편별 락, before/after 재현 |
| 재시작하면 예약이 사라진다 | 메모리 상태는 휘발성 | 스냅샷 → 임시 파일 → `rename()` |
| 모든 기능을 한 프로세스에 두면 묶인다 | 배포·재시작·자원 제한이 같이 묶임 | 경로 기반 게이트웨이 + 별도 백엔드 |
| 결제는 예약과 규칙이 다르다 | 재시도, 환불, 중복 청구 위험 | 별도 결제 서비스, 중복 방지 키, 환불 |

즉, STEP1의 `listen/accept`부터 STEP10의 결제까지는 **따로 놀지 않습니다.**
모두 "바이트 스트림을 신뢰할 수 있는 요청-응답으로 바꾼다"는 같은 문제의
다음 층입니다.

## 한 문장 요약

```text
클라이언트가 보낸 바이트를 정확히 한 요청으로 경계 짓고,
여러 요청이 동시에 들어와도 상태가 깨지지 않게 처리하며,
재시작·장애·결제 실패 이후에도 결과를 다시 설명할 수 있게 만든다.
```

이 문서가 프로젝트의 `문제 정의`입니다. 설계는 `DESIGN.md`, 선택 근거는
`DECISIONS.md`, 실행 증거는 `verify/`에 있습니다.
