# HTTP/네트워크 개념 메모

프로젝트 구현과 맞닿은 부분만 정리합니다. 공부 목록이 아니라 우리가 왜 이렇게 골랐는지 위주입니다.

## 1. 멀티프로세스 vs 멀티스레드

- 지금 구조: 단일 프로세스 + 워커 스레드 N개(D5). 좌석 상태를 뮤텍스로 공유.
- `fork` 구조로 바꾸면: 프로세스마다 좌석이 따로 놀아 공유 메모리/IPC가 필요하고, accept 분산·좀비 처리·재기동이 복잡해짐. 대신 프로세스 격리는 좋음.
- 요구사항 FR-06은 “멀티스레드 또는 멀티프로세스 중 하나 이상”이라 둘 다 해당. 우리는 스레드 + 이벤트 루프 선택.

## 2. 느린 백엔드 격리 (전용 스레드 + 큐)

- 워커가 백엔드 응답을 기다리면 그 워커는 다른 요청을 못 처리함.
- 프록시 요청이 오면 워커는 작업을 큐에 넣고 즉시 반환. 전용 스레드 `proxy_thread_main`이 큐에서 꺼내 백엔드와 통신.
- `dup()`으로 client fd를 복사해 소유권을 넘김.
- 효과: 느린 백엔드가 2초 걸려도 `/health`는 0ms.

## 3. 리버스 프록시가 백엔드를 숨기는 방식

- 클라이언트는 한 포트(8085)만 봄.
- `conf/backends.conf`의 `route = prefix|backend...`가 경로와 백엔드 매핑을 들고 있음.
- 백엔드 주소·포트·대수가 바뀌어도 클라이언트는 그대로.
- 포워드 프록시는 반대 방향(클라이언트 대신 외부로 나감).

## 4. Host 헤더

- HTTP/1.1: 한 IP에 여러 도메인이 있을 때 어느 사이트로 갈지 `Host`로 구분(가상 호스팅). 없으면 400.
- HTTP/2: `:authority` 의사 헤더가 그 역할을 대신. `Host`는 호환용.

## 5. HTTP 응답 확인 대상

- 헤더와 본문 둘 다. 상태 줄, `Content-Type`, `Content-Length`, `Connection` + 본문 길이·바이너리 무결성.

## 6. 요구사항이 요구하는 HTTP 이해

- 요청 라인(메서드·URI·버전), 헤더(Host·Content-Length·Connection), 본문 경계, 상태 코드, keep-alive 규칙, MIME, 경로 보안, 프록시 요청 형태.

## 7. 로드밸런싱

- 프록시가 여러 백엔드로 나누는 행위가 로드밸런싱. `/api/orders/` → 8401, 8402 Round-Robin.
- 목적은 확장(백엔드 추가)과 장애 분산.

## 8. HTTP 파싱

- 바이트 스트림에서 요청의 경계와 구조를 복구. `\r\n\r\n` 검색 → 요청 줄 분해 → 헤더 순회 → `Content-Length`로 본문 끝.

## 9. 프로토콜 버퍼

- protobuf는 직렬화 형식. 우리는 JSON 최소 구현(D8). gRPC는 HTTP/2 + protobuf이며 미구현.

## 10. HTTP/2 멀티플렉싱

- 한 TCP 연결 위에서 여러 스트림을 프레임으로 섞어 보냄. “한 패킷”이 아니라 프레임 단위.
- 수신쪽은 프레임의 `stream id`로 각 스트림을 다시 재조립함.
- 우리는 HTTP/1.1이라 한 연결에서 순서대로 처리. keep-alive는 재사용이지 동시 처리가 아님.
- 소켓은 클라이언트 연결마다 하나. 브라우저가 병렬 연결을 열면 여러 개.

**이름만 같고 다른 장치라는 점을 구분한다.** HTTP/2 '멀티플렉싱'은 공식 용어지만, 이 프로젝트의 I/O 멀티플렉싱(`epoll`)과는 층이 다르다.

| | HTTP/2 스트림 멀티플렉싱 | I/O 멀티플렉싱(`epoll`) |
|---|---|---|
| 무엇을 섞나 | 하나의 TCP 연결 위 여러 요청·응답 | 한 스레드가 감시하는 여러 fd |
| 구분 수단 | 프레임의 `stream id` | fd 번호와 커널의 준비 목록 |
| 누가 구분하나 | 수신쪽이 프레임을 재조립 | 커널이 준비된 fd만 알려줌 |
| 관계 | 전송 계층(HTTP) | 시스템 호출 계층(I/O) |

그래서 "멀티플렉싱을 하면 HTTP/2가 되는가"는 성립하지 않는다. 우리는 h2를 직접 구현하지 않고 앞단 게이트웨이에 맡긴다(D26).

## 11. 순서 보장

- TCP는 항상 바이트 순서 보장.
- HTTP/1.1은 한 연결에서 순서 처리 → 앞 요청이 느리면 뒤가 막힘(HOL).
- HTTP/2는 스트림 단위 독립 → 앱 계층 순서는 강제 안 함. 단 TCP HOL은 남음.
- HTTP/3(QUIC)이 TCP HOL 제거.

## 12. Envoy와 영구 연결

- Envoy 같은 프록시는 upstream 연결 풀을 유지해 keep-alive 자동 관리.
- 앞단에 Envoy를 두면 클라이언트-Envoy, Envoy-우리 서버 사이 풀링을 해줌. 우리 서버도 keep-alive 지원 필요(지금 지원).

## 13. 대역폭과 지연

- 대역폭 = 초당 전송량, 지연 = 첫 바이트까지 시간.
- 대역폭이 좁으면 큰 파일 전송 시간이 길어지고, 링크 포화 시 큐잉 지연 발생.
- 우리 시연의 지는 대역폭이 아니라 느린 백엔드·느린 클라이언트.

## 14. TLS와 대칭키

- 비대칭 암호는 실제 데이터에 쓰기엔 느림. 핸드셰이크로 대칭 키를 합의하고 이후 데이터는 대칭키로 암호화.
- 인증서는 서버 진위 확인. 우리는 TLS 미구현(범위 밖), 실배포는 앞단 게이트웨이에서 종료(D26).

## 15. 서버 한 개, 클라이언트 여러 개

- 우리 서버는 한 프로세스가 여러 클라이언트 연결을 동시에 받음.
- 채팅 서버는 같은 형태. 실시간 양방향은 WebSocket/SSE·롱폴링 필요. 우리 keep-alive는 서버 푸시 없음.
- 암호화는 TLS, 동시 접속은 워커 풀로 처리.

## 16. 챗봇 Q&A 적용 가능 범위

- 동시 접속·동적 요청 처리(FR-05, FR-06)는 지금 구조로 가능.
- 실시간 푸시는 요구사항에 없고 미구현 → 별도 확장.
- 암호화는 앞단 TLS 종료로 붙일 수 있음.

## 17. 소켓 식별 (4-tuple)

- 소켓은 `<protocol, IP, port>`로 **정의**한다. `SOCK_STREAM`은 TCP.
- 커넥션은 소켓 주소 두 개, 즉 `<src IP, src port, dest IP, dest port>`로 **식별**한다.
- 서버에서 리스닝 소켓과 각 연결 소켓은 로컬 IP·포트가 같을 수 있다. `dest`만으로는 구분이 안 되니 `src`까지 함께 본다.
- 우리 코드가 이 식별을 직접 하지 않는다. 커널이 4-tuple로 분류해 해당 `fd`로 전달하고, 우리는 `getpeername()`으로 클라이언트 IP만 읽어 접근 로그에 쓴다(`src/connection.c`).
- “TCP 표준에서는 IP·port가 유니크해야 해서 실제 동작과 다르다”는 표현은 부정확하다. 소켓 주소를 식별하는 단위와 커넥션을 식별하는 단위가 다르다는 말이 맞다. RFC 793도 커넥션을 소켓 쌍으로 식별한다.

## 18. 동시성과 병렬성

- **동시성(concurrency)**: 여러 작업이 겹치는 시간대에 진행되는 것. 번갈아 실행(인터리빙)도 포함이라 코어 1개로도 성립한다.
- **병렬성(parallelism)**: 여러 작업이 같은 순간에 실제로 같이 도는 것. 물리적 코어가 필요하다.
- 이 서버는 둘을 섞는다. 동시성은 워커 4개가 각자 여러 연결을 돌아가며 처리하는 데서 나오고(`iomux`), 병렬성은 워커 4개가 코어 4개에서 동시에 도는 부분에서 나온다.
- 그래서 CPU 바운드 작업은 스레드 수로 늘리고, I/O 대기는 이벤트 루프로 겹친다.
