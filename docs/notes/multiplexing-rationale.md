# 이 프로젝트에서 I/O 멀티플렉싱을 고른 이유

## 한 줄 요약
웹서버의 "동시 연결이 많고, 대부분은 유휴며, 요청 하나는 짧고, 느린 클라이언트가 섞여 있다"는 성격이, 연결마다 스레드/프로세스를 두는 방식 대신 **고정된 수의 워커 + 논블로킹 소켓 + 이벤트 루프**를 요구했고, 그 과정에서 Linux의 `epoll`(macOS의 `kqueue`, 폴백은 `poll`)이 선택됐다.

---

## 1. 웹서버의 성격 — 멀티플렉싱이 필요했던 이유

네 가지 성격이다. 이 성격이 멀티플렉싱이 "더 좋아서"가 아니라 "없으면 안 되는" 이유다.

1. **동시 연결이 많다.** 브라우저는 도메인당 여러 연결을 병렬로 열고, keep-alive로 같은 연결을 계속 쓴다. 사용자 수가 늘면 연결 수는 선형으로 늘어난다.
2. **요청 하나의 일은 짧다.** 정적 파일 요청이면 "파일을 읽고 응답을 쓰는 것"이 전부다. 긴 계산이 아니다.
3. **대부분의 시간은 유휴.** 클라이언트가 다음 요청을 보내기까지 소켓에 데이터가 없다. 연결은 살아 있는데 할 일은 없는 상태가 길다.
4. **느린 클라이언트가 섞여 있다.** 모바일 네트워크처럼 데이터를 천천히 보내는 클라이언트가 있다.

이 성격에서 블로킹 모델의 대가가 드러난다.

- 연결당 스레드/프로세스를 두면, 유휴 시간 동안 그 스레드는 자원을 점유한 채 일하지 않는다. 느린 클라이언트는 자기 스레드를 오래 붙잡고, 연결이 1000개면 스레드도 1000개가 된다.
- 스레드를 많이 만들면 컨텍스트 스위치가 늘고, 스레드 스택(대부분 8MB 가상)이 그대로 늘어난다. 하나의 큰 요청이 하나의 스레드를 오래 붙잡는 동안 다른 연결은 진행되지 못한다.

멀티플렉싱은 이 구조를 뒤집는다. 스레드 수는 고정해 두고, 스레드는 "지금 준비된 연결"만 처리한다. 유휴 연결은 커널의 소켓 버퍼에 있을 뿐 스레드를 차지하지 않는다. 느린 클라이언트는 `READ` 이벤트가 늦게 도착할 뿐, 다른 연결 처리를 막지 않는다. 그래서 연결 수가 늘어도 스레드 수는 늘리지 않는다.

## 2. 왜 이 프로젝트는 "멀티스레드 + 멀티플렉싱"인가 (왜 멀티프로세스가 아닌가)

이 프로젝트는 공유 상태를 유지한다(항공편 데모의 좌석 배열 등). 그 상태를 여러 프로세스로 찢으면 다음 문제가 생긴다.

- **메모리 복사본** — `fork()`는 자식에게 부모 메모리를 복사한다. 좌석 배열이 워커마다 따로 존재하게 되어, 프로세스 간 동기화가 새로 필요하다.
- **프로세스 간 통신** — 공유 상태만 생각하면 세마포어/공유 메모리, 또는 메시지 큐가 필요해진다. 같은 프로그램 안에서 상태만 공유하면 되는 경우, 비용만 커진다.
- **파일 디스크립터 핸드오프** — 워커 사이에 fd를 넘기는 것도 복잡해진다. 이 프로젝트는 accept한 워커가 연결을 끝까지 소유해 fd 핸드오프가 없다.

그래서 이 프로젝트는 "연결 처리 = 멀티플렉싱"과 "공유 상태 = 스레드 + 뮤텍스"를 분리했다. 두 가지를 섞으면 문제가 풀린다.

- 연결 처리가 병목이면 멀티플렉싱으로 많은 fd를 돌리고(스레드는 적음),
- 상태 경쟁이 병목이면 뮤텍스 하나로 정확히 처리한다.

즉, "연결을 어떻게 처리할 것인가"와 "공유 상태를 어떻게 동기화할 것인가"는 서로 다른 층이고, 각각 다른 기술로 풀었다.

---

## 3. 왜 `epoll`(Linux) / `kqueue`(macOS), `poll`은 폴백인가

웹서버의 방향은 "동시 연결은 많고 그중 활성은 적다"이다. 감시할 fd 전체를 매 호출마다 훑는 방식은 이 방향에서 확장되지 않는다.

- `select`/`poll`: `epoll_wait`/`kevent`처럼 fd를 등록하고 준비된 것만 돌려받는 구조가 아니라, 매 호출마다 관심 fd 목록을 커널에 넘기고 커널도 전체를 훑는다. fd가 1000개면 1000개를 매번 본다. 그중 준비된 것은 몇 개뿐이어도 마찬가지.
- `epoll`/`kqueue`: 관심 집합을 커널에 미리 등록해 두고, 준비된 fd만 돌려받는다. fd가 늘어나도 훑는 범위는 준비된 수에만 비례한다.

그래서 "동시 연결이 많고 그중 활성은 적다"는 웹서버의 성격이 `epoll`/`kqueue`를 골라야 할 이유가 된다. `epoll`은 Linux 전용이므로 macOS에서는 `kqueue`, 그 외에서는 POSIX 표준 `poll`을 폴백으로 둔다. 이 분기기는 `src/iomux.c`에 전부 숨기고, 워커 코드는 플랫폼마다 바뀌지 않는다.

## 4. 우리 코드에서 실제로 일어나는 일

1. `worker_pool_start()`가 워커를 `pthread_create`한다(`main.c`). 각 워커는 자기 `iomux` 인스턴스를 만든다(`worker.c`).
2. `iomux_create()`가 플랫폼에 따라 `epoll_create1(0)` / `kqueue()` / `poll` 중 하나를 만들고, `iomux_add()`로 리스너를 등록한다.
3. `while (!*w->stop)` 루프에서 `iomux_wait(mux, events, MAX_EVENTS, 200ms)`를 부른다. 200ms 타임아웃을 주는 이유는, 준비된 이벤트가 없어도 주기적으로 유휴 연결을 정리하고 종료 플래그를 확인하기 위해서다(스케줄링 이벤트인 `event-loop.md`의 내용과 같다).
4. 준비된 이벤트가 오면 `accept()` / `on_readable` / `on_writable`을 부른다.
5. `accept()`에서 새 소켓은 `O_NONBLOCK`으로 만든다. 논블로킹이라 `recv()`가 바로 데이터를 주지 않아도 `EAGAIN`으로 돌아오고, `iomux_mod()`로 `EPOLLOUT`을 다시 등록해 쓰기를 계속한다.
6. `recv()`로 읽은 데이터는 `recv_buf`에 누적한다. 이전에는 수신 버퍼가 8KB로 고정돼서 8KB를 넘는 정상 요청이 431로 실패했지만, 지금은 `connection_feed()`가 버퍼를 동적으로 키운다(`include/connection.h`의 `CONN_RECV_CAP`/`CONN_RECV_MAX`).
7. 요청이 끝나고 응답이 준비되면 `EPOLLOUT`를 등록해 `send()`를 진행한다. 쓰기가 부분 성공하면 `EPOLLOUT`를 다시 등록해 나머지를 나중에 보낸다.
8. 클라이언트가 연결을 닫으면 `recv()`가 0을 돌려주거나 `EPOLLERR`/`EPOLLHUP`가 보이고, `iomux_del()` + `close()`로 정리한다.

레벨 트리거(LT)를 쓴다. `EPOLLET`를 쓰지 않는 이유는, LT가 "읽을 데이터가 있다"는 상태가 유지되는 동안 계속 알려줘서 부분적으로 읽어도 다음 호출에서 다시 알려주기 때문이다. 원문이 "단순하고 쓰기 쉽다"고 한 것도 같은 이유다.

---

## 5. 멀티플렉싱이 다루지 않는 것

멀티플렉싱은 "연결 기계(connection machinery)"를 다루는 기술이지, "도메인 로직"은 아니다.

- 공유 상태는 별도 뮤텍스로 처리한다.
- 결제 게이트웨이나 외부 백엔드 호출은 이 단계의 책임 범위가 아니다.

"연결을 어떻게 처리하고, 공통 욕구를 어떻게 풀 것인가"는 서로 다른 층이다.

## 6. 검증

- `make test` — 단위/통합 테스트가 모두 통과한다(수신 버퍼 동적 확장, 경로 탈출, Content-Length 숫자 검증 등 회귀 테스트 포함).
- `make integration`, `make edge-cases` — 연결 수명, 큰 본문(8KB 정상 / 1MB+1 거부), 비정상 요청 후 생존 확인.
- 실제 빌드에서 이 프로젝트가 도는 플랫폼(macOS)은 `kqueue` 백엔드, Linux에서는 `epoll` 백엔드가 선택된다. `http_parser.c`, `http_response.c`, `static_handler.c`, `connection.c`의 패치가 반영되어 `make test`가 통과한다.
