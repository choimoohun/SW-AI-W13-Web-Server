## 기능과 경계

2026-11-25에 WSL Ubuntu의 루프백에서 C17 소스를 빌드해 기존 회귀 테스트 2개와 별도 실행 시나리오 26개를 통과했다.

| 시나리오 | 관찰 결과 |
| --- | --- |
| 정상 조회·예약·재조회·중복 예약 | `200 → 201 → 200 → 409`. 재조회에 예약 상태가 반영됐다. |
| 동일 좌석 동시 예약 | `201`과 `409`가 한 건씩 나왔다. |
| 백엔드 연결 실패 | API는 `502`, 정적 페이지는 `200`이었다. |
| 백엔드 응답 지연 | API는 3.005초 후 `504`였다. 그동안 별도 연결의 정적 응답은 약 4ms 만에 완료됐다. |
| 작업 큐 포화와 회복 | 워커 4개와 대기 FD 8개를 채운 뒤 받은 추가 연결에 `503`을 확인했다. 포화 해소 뒤 정적 요청은 `200`이었다. |
| 불완전한 요청과 잘못된 입력 | 미완성 헤더는 5.006초 후 `408`이었다. 잘못된 본문·누락 헤더·초과 크기 등은 의도한 오류 코드로 응답했다. |
| 종료 | 유휴 `SIGINT`는 약 30ms에 종료됐다. 연결과 큐가 남은 `SIGTERM`은 약 4.71초에 정리됐다. |

[자동 회귀 테스트](../tests/http_runtime.pl)는 위 핵심 경로와 잘못된 `Connection` 옵션, 정상 `204` 응답도 포함한다. 실행 방법은 [README](../README.md#빌드-및-검증)에 있다.

같은 날 개선 후 Docker에서 `-Wall -Wextra -Wpedantic -Werror` 빌드와 CTest 3개가 통과했다. `http_runtime`은 별도로 연속 두 번 더 통과했다.

## 부하 기준값

2026-11-25 WSL Ubuntu 루프백에서 Python HTTP 클라이언트를 사용했다. 서버와 요청 생성기는 같은 환경에서 실행했고, 경로·동시성 조합마다 약 4초간 측정했다. 처리량과 p95는 **`200` 응답만** 집계했다.

| 경로 | 동시 요청 | 전체 | `200` | 성공 req/s | 성공 p95 | `503` | 기타 오류 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `/` | 4 | 5,914 | 5,914 | 1,478.2 | 3.68 ms | 0 | 0 |
| `/` | 16 | 7,205 | 6,087 | 1,517.7 | 14.80 ms | 1,118 | 0 |
| `/api/seats` | 4 | 10,139 | 10,139 | 2,533.8 | 2.59 ms | 0 | 0 |
| `/api/seats` | 16 | 8,596 | 8,511 | 2,125.4 | 12.39 ms | 85 | 0 |

경로별 응답 크기와 대기 구간이 다르다. 이 수치는 동일 경로가 동시 접속 4건과 16건일 때 어떻게 달라지는지를 보여주는 로컬 기준값이다. Docker의 별도 측정 절차는 [동시 요청 가이드](concurrency/check.md#docker에서-부하-측정)에 있다.

## 추가 부하 및 경계 검증

2026-11-25에 `f69647e`의 서버를 WSL2 Ubuntu에서 GCC 15.2.0으로 빌드했다. 서버와 Python 3.14.4 클라이언트는 같은 WSL의 루프백에서 실행했다. 클라이언트 스레드마다 응답을 받은 뒤 다음 요청을 보내고, 요청마다 새 TCP 연결을 사용했다. 각 부하 구간은 약 4초였다. 지연은 연결을 여는 시점부터 응답 본문을 다 읽을 때까지이며, p95는 표에 적힌 기대 상태 코드로 응답한 요청만 집계한다. 전송 오류는 재시도 없이 따로 센다.

### 단일 경로 재측정

| 경로 | 동시 요청 | 전체 | 200 | 503 | 전송 오류 | 성공 req/s | 성공 p95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `/` | 4 | 2,898 | 2,898 | 0 | 0 | 723.7 | 9.11 ms |
| `/` | 16 | 4,751 | 2,703 | 2,048 | 0 | 672.9 | 33.36 ms |
| `/api/seats` | 4 | 8,000 | 8,000 | 0 | 0 | 1,999.4 | 3.78 ms |
| `/api/seats` | 16 | 5,980 | 5,510 | 470 | 0 | 1,369.8 | 22.13 ms |

이전 표와 경로·동시 접속 수·측정 시간을 맞췄다. 이전에 사용한 요청 생성 코드와 당시의 시스템 부하는 같다고 확인하지 못했으므로 차이를 코드 성능의 향상·저하로 해석하지 않는다.

### 정상·오류 요청을 섞은 부하

각 클라이언트가 다섯 유형을 순환했다. 중복 예약 시나리오를 위해 시작 전에 `1A`를 한 번 예약했다. 기대 응답 건수는 각 요청의 의미에 맞는 응답이다. 예를 들어 없는 경로의 `404`는 기대 결과다.

| 동시 요청 | 시나리오 | 전체 | 기대 응답 | 503 | 전송 오류 | 기대 응답 req/s | 기대 응답 p95 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 정적 GET | 733 | 200 × 733 | 0 | 0 | 183.1 | 29.13 ms |
| 4 | 좌석 조회 | 734 | 200 × 734 | 0 | 0 | 183.3 | 7.33 ms |
| 4 | 없는 API | 731 | 404 × 731 | 0 | 0 | 182.6 | 6.24 ms |
| 4 | 예약 필드 누락 | 732 | 400 × 732 | 0 | 0 | 182.8 | 6.54 ms |
| 4 | 중복 예약 | 732 | 409 × 732 | 0 | 0 | 182.8 | 6.03 ms |
| 16 | 정적 GET | 1,133 | 200 × 770 | 363 | 0 | 191.9 | 44.38 ms |
| 16 | 좌석 조회 | 1,131 | 200 × 758 | 373 | 0 | 188.9 | 24.41 ms |
| 16 | 없는 API | 1,131 | 404 × 794 | 337 | 0 | 197.9 | 25.47 ms |
| 16 | 예약 필드 누락 | 1,131 | 400 × 787 | 39 | 305 | 196.2 | 27.33 ms |
| 16 | 중복 예약 | 1,130 | 409 × 782 | 45 | 303 | 194.9 | 27.14 ms |

| 혼합 부하 · 동시 16 | 측정 시간 | 전체 | 기대 응답 | 503 | POST 전송 오류 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1차 | 4.012 s | 5,656 | 3,891 | 1,157 | 608 |
| 2차 | 4.016 s | 5,437 | 2,765 | 1,779 | 893 |

두 번 모두 전송 오류는 POST에서만 발생했고, Python 클라이언트는 `BrokenPipeError`를 보고했다. HTTP 응답을 읽기 전에 전송이 실패했으므로 해당 요청을 `503` 건수에 포함하지 않았다. 과부하 경로는 [`reject_overload()`](../src/workers.c)에서 이미 도착한 바이트를 한 번 읽고, `503` 전송을 한 번 시도한 뒤 연결을 닫는다. 이 코드와 관찰 결과를 보면 연결 종료가 POST 본문 전송과 겹쳤을 가능성이 있다. 각 실패 연결의 타이밍을 따로 추적하지 않았으므로 원인은 추정이다.

### 동일 좌석 경합과 백엔드 복구

매 회차 백엔드를 새로 시작하고, 빈 좌석 `1A`에 POST 8건을 한꺼번에 보냈다. 1차와 2차 모두 **12회 전부 201 한 건·409 일곱 건**이었고, 재조회에서도 12회 모두 `1A.available=false`를 확인했다. 같은 프록시를 유지한 채 백엔드 중단과 재시작도 12회 반복했다.

| 시나리오 | 표본 | 1차 관찰값 | 1차 p95 |
| --- | ---: | --- | ---: |
| 같은 좌석 동시 예약 | 96건 | 201 × 12, 409 × 84 | 201은 3.86 ms, 409는 4.59 ms |
| 백엔드 중단 중 API 조회 | 12건 | 502 × 12 | 14.48 ms |
| 백엔드 중단 중 정적 GET | 12건 | 200 × 12 | 3.74 ms |
| 백엔드 재시작 후 API 조회 | 12건 | 200 × 12 | 0.83 ms |
| 경합 후 좌석 재조회 | 12건 | 200 × 12, 예약 상태 반영 12회 | 0.72 ms |

두 부하 실행 모두 유휴 상태의 FD 수는 프록시와 백엔드가 각각 `6 → 6`이었다. 같은 GCC 빌드에서 기존 Perl 테스트 3개를 각각 재실행해 통과했다. `http_split_post`는 고정 포트 8080을 쓰므로 별도의 Linux 네트워크 네임스페이스에서 실행했다. 이번에는 Valgrind와 브라우저 두 탭 검증을 반복하지 않았다.

### 실행 재현

WSL Ubuntu의 프로젝트 루트에서 실행한다. 테스트가 로컬의 빈 포트에 프록시와 백엔드를 직접 띄우고 종료한다. 서버 빌드는 임시 디렉터리에 둔다.

```sh
build_dir=$(mktemp -d /tmp/week13-load.XXXXXX)
gcc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Wpedantic -Werror -pthread \
    src/main.c src/http.c src/booking.c src/proxy.c src/io.c src/workers.c \
    -o "$build_dir/web_server"
python3 tests/http_load.py "$build_dir/web_server" > "$build_dir/measurements.json"
```

[`http_load.py`](../tests/http_load.py)는 관찰값을 JSON으로 출력한다. 기대 상태와 `503` 외에 전송 오류 등이 발견되면 출력 후 종료 코드 1을 반환한다. 두 추가 실행에서 이 종료 코드를 확인했다.

## 자원 검사

- WSL 부하 실행 전후의 유휴 FD 수는 프록시와 예약 백엔드 모두 `6 → 6`이었다.
- Docker에서 Valgrind Memcheck로 정적 응답, 조회·예약·재조회·중복 예약, 종료를 확인했다. 프록시와 백엔드 모두 오류 0건, 종료 시 힙 할당 0바이트를 기록했다. 표준 FD 외에는 Valgrind가 연 로그 FD가 표시됐다.
