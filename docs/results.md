# 검증 결과

## 기능과 예외 처리

자동 회귀 테스트 3개가 통과했다. 분할 POST, 정적 파일 서빙, 예약·프록시·동시 처리를 확인했다. [단계별 검증](testing.md)

| 테스트 | 결과 |
| --- | --- |
| 좌석 조회 → 예약 → 재조회 → 중복 예약 | `200 → 201 → 200 → 409`. 재조회에 예약 상태가 반영됐다. |
| 같은 좌석에 예약 8건 동시 요청 | 두 실행에서 각각 12회 검증했다. 매 회차 `201` 1건과 `409` 7건이 나왔고, 재조회에서 좌석이 예약된 상태였다. |
| 백엔드 중단 → 재시작 | 두 실행에서 각각 12회 검증했다. 중단 중 API는 `502`, 정적 페이지는 `200`이었다. 재시작 후 API는 모두 `200`으로 복구됐다. |
| 백엔드 응답 지연 | API는 약 3초 뒤 `504`를 반환했다. 그동안 다른 연결의 정적 요청은 약 4ms에 완료됐다. |
| 큐 포화와 회복 | 워커 4개와 큐 8칸이 찬 상태에서 추가 요청에 `503`을 확인했다. 포화가 풀린 뒤 정적 요청은 `200`이었다. |
| 미완성 요청과 잘못된 입력 | 미완성 헤더는 약 5초 뒤 `408`이었다. 헤더 누락, 잘못된 본문, 크기 제한 초과도 기대한 오류 코드로 응답했다. |
| 종료 및 자원 정리 | 유휴 상태의 `SIGINT`는 약 30ms, 활성 연결과 큐가 남은 상태의 `SIGTERM`은 약 4.7초에 종료됐다. 부하 전후 유휴 FD는 프록시와 백엔드 모두 `6 → 6`이었다. Valgrind 검사에서 두 프로세스 모두 오류 0건, 종료 시 남은 힙 0바이트였다. |

## 부하 테스트

각 구간은 약 4초다. 단일 경로의 처리량과 p95 지연은 `200` 응답 기준이다.

| 경로 | 동시 요청 | 기준 측정 성공 req/s · p95 | 재측정 성공 req/s · p95 | `503` 건수 (기준 → 재측정) |
| --- | ---: | ---: | ---: | ---: |
| 정적 페이지 | 4 | 1,478.2 · 3.68 ms | 723.7 · 9.11 ms | 0 → 0 |
| 정적 페이지 | 16 | 1,517.7 · 14.80 ms | 672.9 · 33.36 ms | 1,118 → 2,048 |
| 좌석 조회 | 4 | 2,533.8 · 2.59 ms | 1,999.4 · 3.78 ms | 0 → 0 |
| 좌석 조회 | 16 | 2,125.4 · 12.39 ms | 1,369.8 · 22.13 ms | 85 → 470 |

단일 경로에서는 전송 오류가 없었다. 두 측정의 실행 조건이 완전히 같았는지 확인하지 못했으므로 처리량 차이의 원인은 판단을 보류한다.

### 정상·오류 요청 혼합

정적 페이지, 좌석 조회, 없는 API, 필드가 빠진 예약, 중복 예약을 섞어 보냈다. 기대 응답에는 `200`과 요청에 맞는 `400`·`404`·`409`가 포함된다.

| 동시 요청 | 전체 | 기대 응답 | `503` | POST 전송 오류 |
| --- | ---: | ---: | ---: | ---: |
| 4 | 3,662 | 3,662 | 0 | 0 |
| 16 · 1차 | 5,656 | 3,891 | 1,157 | 608 |
| 16 · 2차 | 5,437 | 2,765 | 1,779 | 893 |

동시 요청 16개에서는 두 번 모두 일부 POST가 HTTP 응답을 받기 전에 `BrokenPipeError`로 끝났다. 큐 포화 시 서버가 연결을 닫는 때와 클라이언트가 본문을 보내는 때가 겹쳤을 가능성이 있다. 실제 순서는 추가 확인이 필요하다.

## 추가로 확인할 테스트

- **과부하 상태의 POST** · 헤더와 본문을 보내는 간격을 달리해 `503` 수신 건수와 전송 실패 건수를 비교한다. 서버가 연결을 닫는 시점도 함께 기록한다.
- **브라우저 두 탭 예약** · 같은 빈 좌석을 선택한 뒤 예약해 한 탭에는 성공, 다른 탭에는 충돌 안내가 표시되는지 확인한다.
- **부하 해소 직후 복구** · 동시 요청 수를 낮췄을 때 `503`과 전송 오류가 언제 사라지고 정상 응답 지연으로 돌아오는지 확인한다.
