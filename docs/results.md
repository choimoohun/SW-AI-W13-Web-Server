# 검증 결과

## 기능과 경계

2026-11-25에 WSL Ubuntu의 루프백에서 C17 소스를 빌드해 기존 회귀 테스트 2개와 별도 실행 시나리오 26개를 통과했다.

| 시나리오 | 관찰 결과 |
| --- | --- |
| 정상 조회·예약·재조회·중복 예약 | `200 → 201 → 200 → 409`. 재조회에 예약 상태가 반영됐다. |
| 동일 좌석 동시 예약 | `201`과 `409`가 한 건씩 나왔다. |
| 백엔드 연결 실패 | API는 `502`, 정적 페이지는 `200`이었다. |
| 백엔드 응답 지연 | API는 3.005초 후 `504`였다. 그동안 별도 연결의 정적 응답은 약 4ms 만에 완료됐다. |
| 작업 큐 포화와 회복 | 워커 4개와 대기 FD 8개를 채운 뒤 받은 추가 연결에 `503`을 확인했다. 포화 해소 뒤 정적 요청은 `200`이었다. |
| 불완전한 요청과 잘못된 입력 | 미완성 헤더는 5.006초 후 `408`이었다. 잘못된 본문·누락 헤더·초과 크기 등은 의도한 오류 코드로 응답했다. |
| 종료 | 유휴 `SIGINT`는 약 30ms에 종료됐다. 연결과 큐가 남은 `SIGTERM`은 약 4.71초에 정리됐다. |

[자동 회귀 테스트](../tests/http_runtime.pl)는 위 핵심 경로와 잘못된 `Connection` 옵션, 정상 `204` 응답도 포함한다. 실행 방법은 [README](../README.md#빌드-및-검증)에 있다.

같은 날 개선 후 Docker에서 `-Wall -Wextra -Wpedantic -Werror` 빌드와 CTest 3개가 통과했다. `http_runtime`은 별도로 연속 두 번 더 통과했다.

## 부하 기준값

2026-11-25 WSL Ubuntu 루프백에서 Python HTTP 클라이언트를 사용했다. 서버와 요청 생성기는 같은 환경에서 실행했고, 경로·동시성 조합마다 약 4초간 측정했다. 처리량과 p95는 **`200` 응답만** 집계했다.

| 경로 | 동시 요청 | 전체 | `200` | 성공 req/s | 성공 p95 | `503` | 기타 오류 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `/` | 4 | 5,914 | 5,914 | 1,478.2 | 3.68 ms | 0 | 0 |
| `/` | 16 | 7,205 | 6,087 | 1,517.7 | 14.80 ms | 1,118 | 0 |
| `/api/seats` | 4 | 10,139 | 10,139 | 2,533.8 | 2.59 ms | 0 | 0 |
| `/api/seats` | 16 | 8,596 | 8,511 | 2,125.4 | 12.39 ms | 85 | 0 |

경로별 응답 크기와 대기 구간이 다르다. 이 수치는 동일 경로가 동시 접속 4건과 16건일 때 어떻게 달라지는지를 보여주는 로컬 기준값이다. Docker의 별도 측정 절차는 [동시 요청 가이드](concurrency/check.md#docker에서-부하-측정)에 있다.

## 자원 검사

- WSL 부하 실행 전후의 유휴 FD 수는 프록시와 예약 백엔드 모두 `6 → 6`이었다.
- Docker에서 Valgrind Memcheck로 정적 응답, 조회·예약·재조회·중복 예약, 종료를 확인했다. 프록시와 백엔드 모두 오류 0건, 종료 시 힙 할당 0바이트를 기록했다. 표준 FD 외에는 Valgrind가 연 로그 FD가 표시됐다.
