# 역할별 프롬프트 (Hermes 등에 그대로 붙여 넣기)

역할마다 대화를 따로 열고 `/title`로 이름을 붙인다. 역할끼리는 대화가 아니라 **파일**로 넘긴다.
다시 열 때는 `hermes -c "기획"`처럼 이름으로 연다. 규칙은 루트 `AGENTS.md`를 따른다.

| 역할 | 대화 이름 | 받는 것 | 내놓는 것 |
|---|---|---|---|
| 기획(설계 포함) | `기획` | 요구사항, 이전 결정 | `docs/iterations/<작업이름>.md` |
| 구현 | `구현` | 위 파일의 작업 하나 | 테스트와 코드 변경(커밋 안 함) |
| 검증 | `검증` | `git diff` + 수용 기준, 또는 문서의 주장 | 역추적 검증 결과 표 |

시작: 저장소 폴더에서 `hermes` 실행 → 입력창에 아래 블록을 붙여 넣는다. `<...>`만 바꾼다.

---

## 1. 기획

```text
/title 기획
```

```text
기획 역할로 해줘. 코드는 고치지 마.
할 일: <하고 싶은 것>
docs/REQUIREMENTS.md, docs/DESIGN.md, docs/DECISIONS.md를 읽고
docs/iterations/<작업이름>.md에 작업 목록(작게 쪼갠 번호 목록), 각 작업의 수용 기준(어떤 make 명령이 무엇을 출력하면 끝인지),
바뀌는 설계와 결정 초안을 써줘. 정해야 할 게 있으면 선택지와 추천을 같이 적어줘.
```

→ 사람이 파일을 읽고 확인한다(첫 번째 사람 체크).

## 2. 구현

```text
/title 구현
```

```text
구현 역할로, docs/iterations/<작업이름>.md의 <번호>번 작업만 해줘.
docs/agent/skills/test-driven-development/SKILL.md 절차대로 실패하는 테스트를 먼저 만들고 실패를 보여준 다음 고쳐.
막히면 docs/agent/skills/debugging-and-error-recovery/SKILL.md를 따라.
수용 기준의 make 명령 결과를 그대로 붙여줘. 커밋은 하지 마.
```

## 3-A. 검증 — 방금 바꾼 것

```text
/title 검증
```

```text
검증 역할로 해줘. 코드는 고치지 마.
git diff로 바뀐 것만 보고, docs/iterations/<작업이름>.md <번호>번의 수용 기준이 실제로 맞는지
AGENTS.md의 '리버스 엔지니어링 검증' 절차대로 코드를 거꾸로 따라가고 실행으로 확인해줘.
판정(맞음/틀림/근거 없음) · 근거(파일:줄) · 실행 결과를 표로.
```

→ 괜찮으면 사람이 커밋한다. 문제가 있으면 이 표를 구현 대화에 붙여 다시 시킨다.

## 3-B. 검증 — 프로젝트 전체 점검 (코드를 바꾸지 않았을 때, 발표 전 등)

```text
/title 점검
```

```text
검증 역할로, 프로젝트 전체를 역추적 검증해줘. 코드는 고치지 마.
README.md, docs/DESIGN.md §3, docs/verify/VERIFICATION_MATRIX.md의 PASS 행에서
'구현됨/통과/~한다' 주장을 10개 골라 질문으로 바꾸고,
AGENTS.md의 '리버스 엔지니어링 검증' 절차대로 코드를 따라가고 가능하면 실행으로 확인해.
결과는 docs/records/audits/AUDIT-<날짜>.md에
질문 · 판정(맞음/틀림/문서 낡음/근거 없음) · 근거(파일:줄) · 실행 결과 표로 써줘.
실행할 때 만든 임시 파일은 끝나면 지워줘.
```

## 4. PR 리뷰가 달렸을 때

```sh
make pr-review PR=<번호>
```

```text
docs/agent/skills/pr-review-loop/SKILL.md 절차대로 PR <번호> triage까지만 해줘. 코드는 고치지 마.
```

---

## 주의

- 결과의 "실행 결과" 칸에 실제 명령 출력이 있는지 본다. 추측("통과할 것")이면 다시 시킨다.
- 같은 폴더에서 에이전트 둘을 동시에 돌리지 않는다. 꼭 필요하면 `hermes -w`(별도 worktree)로 연다.
- 커밋·푸시는 사람이 한다.
