## 4. 2026-11-23 오후 문답 (상세)

### 논블로킹 I/O와 멀티플렉싱은 왜 다른가

- 논블로킹 `recv()`: 앱이 직접 호출해서 소켓 수신 큐를 확인. 비어 있으면 `EAGAIN`으로 즉시 반환. 즉 "물어보는 것이 곧 확인"이다.
- 멀티플렉싱(`epoll`): 앱이 소켓을 등록해 두면, 패킷이 도착해 수신 큐가 채워지는 순간 커널이 대기 큐의 콜백을 실행해 ready 목록에 추가하고 `epoll_wait()`를 깨운다. "커널이 알려주는" 방식이다.
- 대기열(소켓 수신 버퍼)에 데이터를 넣는 주체는 커널이다. 서버는 등록과 꺼내기만 한다. `listen` 대기열(backlog)에는 커널이 핸드셰이크 완료 연결을 넣고 `accept()`가 꺼낸다.
- 역할을 나누면: **어떤 fd를 볼지는 서버 앱이 정한다**(`iomux_add()`, `iomux_mod()`). **그 fd가 준비됐는지는 커널이 판단해 알려준다**(`epoll_wait()`의 ready 목록). 커널은 감시 대상을 임의로 정하지 않으므로 "커널이 알려준다"는 말은 준비 판단에만 해당한다.

### "epoll이 감시 중"의 실체

스레드가 돌며 확인하는 것이 아니라, 각 소켓의 대기 큐에 "상태가 바뀌면 나를 불러라"는 콜백을 건 것이다. `epoll_ctl(ADD)` 시점에 콜백이 걸리고, 이후에는 커널이 패킷 처리 중에 알림을 넣어준다.

### 소켓 감시 방식의 종류

블로킹+연결당 스레드, 논블로킹 폴링, `select`, `poll`, `epoll`, `kqueue`, `io_uring`, IOCP, `SIGIO`. 기준은 "누가 조사하나, 얼마나 자주, 몇 개 fd까지". `select`는 `FD_SETSIZE`(보통 1024) 제한이 있고 `poll`은 O(N), `epoll`/`kqueue`는 준비된 것만이라 O(준비 수).

### 멀티스레드/멀티프로세스와 멀티플렉싱은 비교 단위가 아니다

- 멀티스레드/멀티프로세스 = 일하는 주체가 몇 개인가.
- 멀티플렉싱 = 한 주체가 여러 소켓을 어떻게 감시하는가.

Redis = 단일 스레드 + 이벤트 루프(메모리 연산이 짧아 락 없이 원자성 확보). DBMS = 스레드/프로세스 풀(쿼리가 길고 디스크 I/O, 코어 병렬). 우리 = 스레드 4개 + 각자 이벤트 루프(I/O 대기를 겹치고 CPU 일은 병렬).

### 각 요청 대기 시간이 줄어드는 원리

워커의 타임라인이 "한 연결의 생애"가 아니라 "준비된 이벤트 목록"으로 채워지기 때문이다. 예: A의 데이터가 t=50ms에, B·C가 t=10ms에 도착하면,

- 블로킹: A → B → C 순서 처리라 B는 60ms, C는 65ms.
- 이벤트 루프: B(10ms), C(15ms), A(50ms).

겹는 건 "데이터가 오기를 기다리는 시간"이며 CPU 연산은 겹지 않는다. 그래서 CPU 바운드는 스레드 수로 해결한다.

### Envoy란

L4/L7 프록시로 reverse proxy / API gateway / service mesh sidecar 역할을 한다. 로드밸런싱, TLS 종단·mTLS, HTTP/2·gRPC, 서킷브레이커, 재시도, 레이트리밋, 헬스체크, 동적 설정(`xDS`), 메트릭·트레이싱을 제공. Kubernetes+Istio에서 sidecar로, Emissary·Contour·Gloo에서 API gateway 엔진으로 쓰인다. 우리가 직접 만든 L7 로드밸런서는 같은 문제를 더 작게 푼 것이다.

### 멀티프로세스를 붙이는 것이 오버엔지니어링인가

지금 규모에서는 그렇다. 정당화 조건은 워커 장애 격리 필요, 동시 연결이 코어 수를 넘고 CPU 일이 무거움, 공유 상태가 없거나 `shm`으로 감당 가능, 운영상 프로세스별 재기동 필요. 우리는 동시 100~1000 수준이고 좌석 상태를 공유하며 데모 규모라 스레드 4개로 충분하다. "실서비스처럼"은 멀티프로세스 없이 헬스체크, graceful shutdown, 메트릭, 타임아웃, 설정 파일, TLS로 충분하다.

## 2026-11-23 HTTP/1.1 슬로우 스타트

- 질문: HTTP/1.1에서 처음 연결할 때 슬로우 스타트가 일어나는데, 이걸 극복하려면 어떻게 개선하는가?
- 원인: 슬로우 스타트는 TCP 혼잡 제어의 일부다. 새 연결의 혼잡 윈도우(`cwnd`)가 작게 시작해서 점진적으로 늘어나므로, 연결 직후의 전송 속도가 낮다. 혼잡 붕괴를 막기 위한 동작이라 끌 수 없다.
- 그래서 “극복”이 아니라 “영향을 줄이는” 방향이 맞다.
- 줄이는 방법:
  - 연결 재사용(keep-alive): 매 요청마다 새 연결을 맺지 않으면 슬로우 스타트도 한 번만 든다. 우리 서버는 keep-alive을 최대 100회까지 허용한다.
  - 초기 혼잡 윈도우 키우기: Linux `net.ipv4.tcp_initcwnd`나 경로의 `initcwnd` 값. RFC 6928은 초기 윈도우 10 MSS를 권고한다.
  - `net.ipv4.tcp_slow_start_after_idle=0`: 유휴 연결이 다시 데이터를 보낼 때 슬로우 스타트로 돌아가는 것을 방지한다.
  - TCP Fast Open(TFO): 첫 데이터를 핸드셰이크와 함께 보낸다.
  - HTTP/2 또는 HTTP/3(QUIC): 한 연결에서 여러 요청을 멀티플렉싱하고, HTTP/3는 0-RTT로 첫 전송을 앞당긴다.
  - 브라우저가 도메인당 여러 연결(보통 6개)을 여는 것, CDN·지리적으로 가까운 서버, 압축, 첫 바이트까지의 시간 단축.
- 우리 프로젝트에서 지금 할 수 있는 것은 keep-alive(이미 적용)와 첫 응답 최적화 정도다. TCP 튜닝은 OS/커널 설정이라 앱 코드 밖이고, HTTP/2·HTTP/3은 요구사항에 없어 범위 밖이다.

## 2026-11-22 왜 `epoll` + 멀티프로세스(하이브리드)인가

- 질문: 발제에서 `epoll()` with multiprocess(하이브리드)가 좋고, multi thread minimum, `epoll()` only 아니고, multiprocess only 아니라고 했다. 이유가 뭔가?
- 답변:
  - `epoll` only(단일 프로세스 단일 스레드 이벤트 루프): 코어를 하나밖에 못 쓴다. 요청 처리가 길어지면 프로세스 전체가 막힌다. 동시 연결은 잘 처리하지만 CPU 집중 작업에 약하다.
  - multiprocess only(블로킹 멀티프로세스): 프로세스 수만큼 메모리와 컨텍스트 스위치 비용이 든다. 연결마다 프로세스를 띄우면 동시 접속이 늘 때 무겁다. 공유 상태(좌석)도 프로세스 간 공유가 어렵다.
  - 멀티스레드: 프로세스보다 가볍지만 같은 주소공간이라 동기화가 필요하고, 한 스레드의 크래시가 전체를 죽인다. 그래서 "minimum"이라 했을 것이다.
  - 하이브리드: 프로세스를 코어 수만큼 띄우고, 각자가 `epoll` 이벤트 루프를 돈다. 코어를 다 쓰고 프로세스 격리도 얻고, 블로킹 멀티프로세스보다 가볍다. nginx와 Envoy가 이 구조다.
  - 우리 선택은 프로세스 대신 스레드. 이유는 좌석 공유 비용(공유 메모리·IPC가 필요). 대가는 크래시 격리 부재.

## 2026-11-22 CGI/FastCGI, Next.js·SSG·SOA·REST API는 범위인가

- 질문: fastcgi가 결국 스레드 풀인가? cgi가 매번 재사용인가? next.js, ssg, soa, restapi는 이번 과제 범위인가?
- 답변:
  - CGI: 요청마다 프로세스를 실행한다. 매번 새로 만들고 종료한다. 재사용이 아니다. 질문의 "cgi가 매번 재사용"은 반대다.
  - FastCGI: 프로그램(프로세스)을 띄워 두고 요청을 재사용한다. 스레드 풀과 비슷한 효과를 프로세스로 얻는 방식이다.
  - 우리 프로젝트: FR-05에서 안 A(CGI)를 버리고 안 B(내장 동적 핸들러 + 백엔드 프록시)를 골랐다. FastCGI도 범위 밖이다.
  - Next.js/SSG: 프레임워크다. 우리는 C로 직접 만드는 것이 목표라 범위 밖이다.
  - SOA/REST API: 개념은 관통한다. `/api/...`가 REST 스타일이고, 프록시 모듈이 게이트웨이의 일부 역할을 한다. 다만 프레임워크를 쓰지는 않는다.

## 2026-11-22 직렬화, `send_all`, 청크 전송 용어

- 질문: 직렬화, `send_all`, 청크 전송처럼 실무에서 다 아는 용어인지 확인해 달라.
- 답변:
  - 직렬화: 구조체·객체를 바이트열로 바꾸는 것. JSON, protobuf가 직렬화 형식이다. 우리 `http_response_build_*()`가 문자열을 버퍼에 순서대로 나열하는 것도 직렬화에 해당한다. 실무 용어 맞다.
  - `send_all`: POSIX 표준 함수는 아니다. `send()`가 부분 쓰기(short write)를 할 수 있어서 "남은 바이트를 계속 보내는 루프"를 흔히 그렇게 부른다. 설명할 때는 "partial write 처리"가 더 정확하다.
  - 청크 전송: HTTP `Transfer-Encoding: chunked`의 번역이다. 실무 용어 맞다. 다만 우리 문서에서 "파일을 16KB 단위로 나눠 본내는 것"을 청크 전송이라고 쓴다. HTTP의 chunked 인코딩과는 다른 의미이므로 문서에서 구분을 명시해야 한다.
