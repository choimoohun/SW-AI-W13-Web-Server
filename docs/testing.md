# 단계별 검증

[설계 목차](design.md) · [실제 검증 기록](progress.md) · [동적 기능 실행 명령](dynamic/check.md)

| 작업 | 합격 기준 |
| --- | --- |
| [예약 API](dynamic/booking.md) | 최초 조회 후 빈 좌석을 예약하면 `201`이고 재조회에서 예약 상태가 보인다. 같은 좌석 재예약은 `409`다. 잘못된 입력과 없는 좌석도 확인한다. |
| [프록시](dynamic/proxy.md) | `curl`로 웹 서버를 거쳐 GET·POST를 보낸다. 백엔드 중단 시 `502`, 응답을 지연시켰을 때 `504`를 확인한다. 이후 정상 요청과 기존 정적 파일·분할 POST 테스트를 다시 확인한다. |
| [순차 연결](concurrency/connections.md) | 첫 연결을 정리한 뒤에도 두 번째 요청이 처리된다. 브라우저에서 페이지를 연 뒤 API 조회·예약·충돌 응답을 확인한다. |
| [워커 풀](concurrency/workers.md) | 예약 응답을 보류한 상태에서 다른 연결의 정적 GET이 먼저 끝난다. 같은 좌석에 겹쳐 들어온 예약은 `201` 한 건, `409` 한 건이다. 큐를 채운 뒤 추가 연결의 처리를 확인한다. |
| [종료](concurrency/shutdown.md) | 유휴 상태와 처리 중인 상태에서 각각 종료 신호를 보내고 대기·활성 연결과 워커가 정리되는지 확인한다. |

1.6에서는 로컬 테스트 환경에서 정적 GET과 좌석 조회의 동시 접속 수를 단계적으로 올리고, 요청 유형·동시 접속 수·측정 시간과 함께 처리량·지연·실패율을 남긴다. 예상된 `409`와 과부하 거절은 예상 밖 실패와 구분한다. 1.7에서는 같은 조건으로 다시 측정하고, 정상·예외 요청을 섞어 검증하며 FD 회수와 sanitizer 또는 Valgrind 결과를 확인한다.
