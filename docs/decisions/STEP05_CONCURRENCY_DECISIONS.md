# 동시 요청 처리 결정

STEP5에서 확정한 결정과 트레이드오프. STEP1~4 결정은 각 STEP 문서를 참고한다.

| ID | 결정 사항 | 배경 및 사유 | 트레이드오프 |
|---|---|---|---|
| D5 | 워커별 이벤트 루프: 워커 스레드 N개, 각자 `iomux`(epoll/kqueue/poll) 루프. 단일 프로세스 | 한 프로세스에서 공유 상태(좌석)를 그대로 쓰면서, 연결 처리는 여러 스레드로 나눠 돌리기 위해. `fork`를 쓰면 공유 메모리·좀비 회수·재기동 코드가 필요하고, `accept`한 쪽이 연결을 넘겨줘야 한다 | 프로세스 간 크래시 격리는 없음. 워커별 루프 코드가 늘어난다 |
| D9 | epoll(Linux) / kqueue(macOS) 백엔드, 그 외 플랫폼은 poll 폴백 | 준비된 fd만 커널이 통지 → 연결 수에 비례해 전체를 스캔하지 않는다. 같은 `iomux` 인터페이스라 워커 코드는 불변 | 플랫폼별 `#ifdef` 분기. 현재 구현은 epoll 결과의 fd→연결 포인터를 등록 배열에서 선형으로 찾는다(이벤트당 O(N)). 아래 STEP05 문서의 "알려진 한계" 참고 |
| D10 | keep-alive + 이벤트당 `accept` 1건 | 요청 겹침을 보려면 `accept`를 여러 워커에 분산해야 한다. 한 번에 다 `accept`하면 첫 워커가 독점해 경쟁이 사라진다 | `accept` 시스템콜 수 증가 |
| D25 | Makefile에 `-MMD -MP` 헤더 의존성 추가 | `connection_t` 같은 구조체에 필드를 추가해도 포함 객체가 재컴파일되지 않아 레이아웃 불일치가 났다 | `src/*.d` 파일이 생긴다(`.gitignore` 처리) |
