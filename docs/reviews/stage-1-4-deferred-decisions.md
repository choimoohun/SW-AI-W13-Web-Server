# 1~4단계 리뷰에서 미룬 결정

[1~4단계 코드 리뷰](./stage-1-4-code-review.md)의 수정할 점 중 1, 3, 4번은 고쳤습니다. 이 문서는 방법이 여럿이라 고르지 않고 미룬 세 가지를 정리합니다. 각 항목에 방법별 장단점과 제안을 적었으니, 해당 단계를 설계할 때 근거로 씁니다.

| 항목 | 제안 | 결정할 단계 |
| --- | --- | --- |
| A. 느린 클라이언트가 서버 전체를 막음 (리뷰 2번) | 지금 호출 단위 시간 제한(`SO_RCVTIMEO`, `SO_SNDTIMEO`)을 넣고, 근본 해결은 6단계 동시성에서 | 지금 결정하면 1단계 설계 수정, 아니면 6단계 |
| B. 오류 응답 직후 `close`의 RST (리뷰 5번) | 지금은 두고 6단계에서 keep-alive와 함께 lingering close 설계 | 6단계 |
| C. `*` 형식 요청 대상 (`OPTIONS * HTTP/1.1`) | 지금은 400 유지. 프록시 단계에서 요청 대상 네 형식을 한꺼번에 설계 | 7단계 (결과: C1 유지, C3는 후속) |

2026-11-24에 세 항목 모두 제안대로 결정했습니다. A1은 [연결 시간 제한](../static-file-serving/design.md#연결-시간-제한)으로 적용했고, A3, B2, C4는 각 단계를 설계할 때 이 문서를 근거로 씁니다.

6단계에서 B를 다시 봤습니다. keep-alive를 넣지 않아 "요청을 어디까지 읽고 언제 닫는가"를 다시 설계할 계기가 없었으므로 B2(lingering close)도 keep-alive와 함께 제외했고, 지금은 B1을 유지합니다([동시 요청 처리 범위](../concurrency/design.md)).

2026-11-25, 7단계에서 C를 다시 봤습니다. Forward Proxy가 아닌 리버스 프록시를 택해 absolute-form을 받을 필요가 없어졌으므로 C4의 전제가 사라졌습니다. 지금은 C1(400)을 유지하고, C3 규칙(`OPTIONS *`만 통과시켜 501)은 후속으로 미뤘습니다([리버스 프록시 1차 구현 범위](../reverse-proxy/design.md#1차-구현-범위)).

## A. 느린 클라이언트가 서버 전체를 막음

### 문제

`httpd`는 연결 하나를 끝까지 처리한 뒤 다음 `accept()`로 넘어가는 순차 서버입니다. 처리 중인 클라이언트가 아무것도 보내지 않으면 `read()`가 막히고, 응답을 읽지 않으면 송신 버퍼가 차서 `rio_writen()`이 막힙니다. 그동안 다른 클라이언트는 모두 기다립니다. 리뷰에서는 `Content-Length: 10`에 본문을 5바이트만 보내고 연결을 유지해 재현했습니다.

막히는 곳은 세 군데입니다.

| 위치 | 막히는 조건 |
| --- | --- |
| `http_read_head()`의 `rio_readlineb()` | 빈 줄을 보내지 않음 |
| `http_read_body()`의 `rio_readnb()` | `Content-Length`보다 적게 보냄 |
| `static_serve()`, `http_send_*()`의 `rio_writen()` | 클라이언트가 응답을 읽지 않아 송신 버퍼가 가득 참 |

### 방법

#### A1. 호출 단위 시간 제한 (`SO_RCVTIMEO`, `SO_SNDTIMEO`)

`accept()` 직후 `connfd`에 시간 제한을 겁니다.

```c
struct timeval tv = {.tv_sec = 5, .tv_usec = 0};
setsockopt(connfd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof tv);
setsockopt(connfd, SOL_SOCKET, SO_SNDTIMEO, &tv, sizeof tv);
```

제한 시간 안에 바이트가 하나도 오지 않으면 `read()`가 -1과 `EAGAIN`을 반환합니다. RIO는 `EINTR`일 때만 다시 시도하므로 -1이 그대로 올라와 `HTTP_READ_CLOSED`가 되고, 응답 없이 연결을 닫습니다. 쓰기도 같아서 `rio_writen()`이 -1을 반환하고 `static_serve()`가 연결을 끊습니다.

- 장점
  - 코드 네 줄이고 구조를 바꾸지 않습니다. 기존 오류 경로를 그대로 탑니다.
  - POSIX 표준 소켓 옵션입니다.
  - 6단계에서 스레드 풀을 쓰더라도 작업 스레드를 붙잡는 연결을 풀어 주려면 여전히 필요합니다. 버려지는 코드가 아닙니다.
- 단점
  - 제한은 `read()`, `write()` 호출 하나마다 따로 걸립니다. 4초마다 1바이트씩 보내는 클라이언트는 끝까지 통과합니다. 8KB 헤더를 그렇게 보내면 몇 시간 동안 서버를 잡아 둡니다.
  - 순차 서버에서는 제한 시간 자체가 모든 클라이언트의 대기 시간입니다. 5초로 정하면 느린 클라이언트 하나당 다른 클라이언트가 최대 5초씩 기다립니다.
  - 값을 골라야 합니다. 짧으면 느린 회선의 정상 클라이언트가 끊기고, 길면 서버가 오래 멈춥니다. nginx의 기본값(`client_header_timeout`, `client_body_timeout`, `send_timeout`)은 60초지만, 동시 처리 서버라 다른 연결이 기다리지 않기 때문에 가능한 값입니다.
  - 응답 헤더를 보낸 뒤 쓰기 제한에 걸리면 응답이 중간에 잘립니다. 상태 줄은 이미 나갔으므로 연결을 끊는 수밖에 없습니다. 이는 지금의 `EPIPE` 처리와 같습니다.

#### A2. 연결 전체의 마감 시각

연결을 받은 시각에서 `CLOCK_MONOTONIC`으로 마감 시각을 정하고, 읽기 전마다 남은 시간만큼 `poll()`로 기다립니다.

- 장점
  - 바이트를 조금씩 흘려 보내는 클라이언트도 마감 시각에 끊깁니다. A1의 구멍을 막습니다.
- 단점
  - RIO로는 구현할 수 없습니다. `rio_readlineb()`는 한 줄을 읽는 동안 내부에서 `read()`를 여러 번 부르는데, 바깥에서 그 사이에 끼어들 수 없습니다. 남은 시간으로 `SO_RCVTIMEO`를 다시 걸어도 내부 `read()`마다 그 시간을 새로 받습니다.
  - `alarm()`과 `SIGALRM`도 쓸 수 없습니다. 교재의 `Signal()`은 `SA_RESTART`로 등록하고 RIO도 `EINTR`면 다시 읽으므로 `read()`가 깨어나지 않습니다.
  - 결국 `rio_t`를 대신할 읽기 함수를 직접 만들어야 합니다. 2단계 설계의 "같은 `rio_t`로 본문 읽기" 결정까지 다시 손봐야 합니다.
  - 그래도 순차 서버라는 한계는 남습니다. 공격자가 연결을 연달아 열면 마감 시각마다 서버가 멈춥니다.

#### A3. 동시 처리 (CS:APP 12장, 6단계)

연결마다 다른 실행 흐름이 처리하게 합니다.

| 방식 | 교재 | 장점 | 단점 |
| --- | --- | --- | --- |
| 연결마다 프로세스 (`fork`) | 12.2 | 연결끼리 메모리가 분리되어 한 연결의 버그가 다른 연결에 번지지 않음 | 생성 비용이 크고, 프로세스 사이에 상태(캐시 등)를 나누기 어려움. 좀비 회수 필요 |
| 연결마다 스레드 | 12.3 | 구현이 단순하고 상태 공유가 쉬움 | 연결 수만큼 스레드가 생김. 느린 연결이 많으면 스레드가 무한정 늘어남 |
| 미리 만든 스레드 풀 + `sbuf` | 12.5.5 | 스레드 수가 정해져 자원 사용이 일정함. 교재 예제가 있음 | 느린 연결이 작업 스레드 수만큼 모이면 다시 전체가 멈춤. 그래서 A1이 여전히 필요함 |
| I/O 다중화 (`select`, `poll`) 이벤트 루프 | 12.2 | 스레드 하나로 많은 연결을 처리. 연결마다 마감 시각(A2)을 두기 자연스러움 | 요청 파싱을 상태 기계로 다시 짜야 함. RIO의 막히는 읽기와 맞지 않음. 코드량이 가장 큼 |

- 장점
  - 느린 클라이언트 하나가 다른 클라이언트를 막지 않습니다. 근본 해결입니다.
  - keep-alive도 이 단계에서 가능해집니다. 순차 서버에서 연결을 유지하면 같은 문제가 생기기 때문입니다.
- 단점
  - 아직 설계하지 않은 6단계 범위입니다. AGENTS.md에 따라 지금 구현할 수 없습니다.
  - 어떤 방식이든 시간 제한은 따로 있어야 합니다. 동시성은 피해 범위를 줄일 뿐 느린 연결이 자원을 붙잡는 문제는 남습니다.

### 제안: 지금 A1, 6단계에서 스레드 풀 + A1

1. **지금 A1을 넣습니다.** 제한 시간은 5초를 제안합니다.
   - 순차 서버에서는 제한 시간이 곧 다른 클라이언트의 대기 시간이므로 짧은 편이 낫습니다. 루프백과 LAN에서 정상 요청이 한 번의 `read()` 사이에 5초를 넘길 일은 드뭅니다.
   - 네 줄로 리뷰에서 재현한 정지(본문을 덜 보내고 멈춘 클라이언트)가 5초 뒤 풀립니다.
   - 6단계에서도 그대로 씁니다.
2. **6단계는 미리 만든 스레드 풀(12.5.5)을 기본안으로 설계합니다.** 지금의 RIO 기반 막히는 읽기 코드를 그대로 재사용할 수 있고 교재 예제가 있습니다. 이벤트 루프는 파서를 다시 짜야 하므로 동시성 단계 하나에 담기에 큽니다.
3. **A2는 하지 않습니다.** RIO를 버려야 하는 비용에 비해, 순차 서버에서는 얻는 것이 적습니다. 바이트를 흘려 보내는 공격은 6단계에서도 스레드 하나만 잡아 두는 수준으로 줄어듭니다. 그래도 막아야 한다면 6단계에서 이벤트 루프를 고를 때 함께 다룹니다.

A1을 지금 넣으려면 AGENTS.md 규칙대로 [TCP 소켓 서버 설계](../tcp-socket-server/design.md)나 [연결 처리 흐름](../static-file-serving/design.md#연결-처리-흐름)에 다음을 먼저 적어야 합니다.

- 값과 근거
- `setsockopt()`가 실패할 때의 처리. 제안은 경고만 출력하고 계속하는 것입니다. 시간 제한이 없을 뿐 요청은 처리할 수 있기 때문입니다.
- 시간 제한에 걸리면 응답 없이 닫는다는 판정 규칙
- 테스트: 헤더를 반만 보내고 멈춘 클라이언트가 있을 때, 두 번째 클라이언트가 제한 시간과 여유 시간 안에 200을 받는지

## B. 오류 응답 직후 `close`의 RST

### 문제

리눅스는 수신 버퍼에 읽지 않은 데이터가 남은 소켓을 `close()`하면 FIN 대신 RST를 보냅니다(RFC 2525 2.17). RST를 받은 클라이언트는 아직 읽지 않은 응답 바이트를 버릴 수 있어서, 400 응답 대신 `Connection reset by peer`를 볼 수 있습니다.

이 서버에서 요청 바이트를 덜 읽은 채 응답하는 경로는 다음과 같습니다.

| 경로 | 남는 입력 |
| --- | --- |
| 헤더 블록이 8KB를 넘어 400 (Q10) | 헤더 나머지 |
| 헤더 형식 오류로 400, 505 | 헤더 뒤 본문 |
| `Content-Length` 값 충돌로 400 (이번 수정) | 본문 |
| `Transfer-Encoding`으로 501 (이번 수정) | chunked 본문 전체 |

이번 수정으로 본문을 읽지 않고 응답하는 경로가 두 개 늘었습니다. 리뷰에서는 루프백이라 재현되지 않았지만, 실제 네트워크에서는 RTT가 길어 재현될 가능성이 더 높습니다.

### 방법

#### B1. 지금처럼 둠

- 장점: 코드가 없습니다. Q10 테스트도 이미 "400 또는 연결 재설정"을 통과로 봅니다.
- 단점: 클라이언트가 오류 이유를 못 받을 수 있습니다. 서버가 죽거나 멈추지는 않으므로 피해는 진단이 어려워지는 정도입니다.

#### B2. lingering close: `shutdown(SHUT_WR)` 후 남은 입력을 버리고 닫기

응답을 보낸 뒤 쓰기 쪽만 닫아 FIN을 보내고, 클라이언트가 연결을 닫거나 한도에 닿을 때까지 들어오는 바이트를 읽어 버린 다음 `close()`합니다. RFC 9112 9.6이 설명하는 방식이고, nginx(`lingering_close`, 기본 `lingering_time` 30초, `lingering_timeout` 5초)와 Apache가 이렇게 합니다.

```c
shutdown(connfd, SHUT_WR);
/* 총 시간과 총 바이트 한도 안에서 read()가 0이나 오류를 줄 때까지 버림 */
close(connfd);
```

- 장점
  - 표준적인 해결책입니다. 클라이언트가 오류 응답을 안정적으로 받습니다.
- 단점
  - 순차 서버에서는 버리는 동안 다른 클라이언트가 기다립니다. A와 같은 문제를 오류 경로에 하나 더 만듭니다.
  - 계속 보내는 클라이언트를 끊으려면 시간과 바이트 한도가 둘 다 필요합니다. 시간 한도는 A1의 `SO_RCVTIMEO`에 기대야 하므로 A1 없이는 안전하게 만들 수 없습니다.
  - 10~15줄 정도 늘고, 어떤 경로에서 버릴지(오류 경로만인지 모든 응답인지) 정해야 합니다.

#### B3. `SO_LINGER` (참고: 해결책이 아님)

이름 때문에 해결책처럼 보이지만 아닙니다. `SO_LINGER`는 `close()`가 **보내지 못한** 데이터를 얼마나 기다릴지 정할 뿐, **읽지 않은** 입력 때문에 나가는 RST는 막지 못합니다. `{l_onoff=1, l_linger=0}`은 오히려 RST를 강제합니다.

#### B4. 오류를 보내기 전에 본문을 다 읽기

`Content-Length`가 정상이면 본문을 읽은 뒤 오류를 보냅니다. POST의 501이 이미 이렇게 동작합니다. 하지만 이번에 늘어난 두 경로처럼 본문 길이를 알 수 없어서 거부하는 경우에는 쓸 수 없습니다. 일반 해결책이 아닙니다.

### 제안: 지금 B1, 6단계에서 B2

- 재현되지 않았고, 서버의 안정성 문제가 아니라 클라이언트가 오류 이유를 받느냐의 문제입니다.
- 순차 서버에서 B2를 넣으면 A의 정지를 오류 경로에 더 만듭니다. 동시 처리가 생긴 뒤에는 버리는 시간이 다른 연결을 막지 않습니다.
- 6단계는 keep-alive 때문에 어차피 "요청을 어디까지 읽었고, 언제 연결을 닫는가"를 다시 설계합니다. lingering close도 같은 자리에서 결정하는 것이 자연스럽습니다.
- 6단계에서 정할 것: 버리는 대상(오류 응답 뒤만 제안), 시간 한도(제안 2초), 바이트 한도(제안 64KiB).

## C. `*` 형식 요청 대상

### 문제

RFC 9112 3.2는 요청 대상을 네 형식으로 나눕니다.

| 형식 | 예 | 쓰임 |
| --- | --- | --- |
| origin-form | `/index.html?x=1` | 일반 요청. 지금 지원하는 유일한 형식 |
| absolute-form | `http://example.com/a` | 프록시에 보내는 요청 |
| authority-form | `example.com:443` | `CONNECT` |
| asterisk-form | `*` | `OPTIONS *`, 서버 전체에 대한 질의 |

지금은 URI가 `/`로 시작하지 않으면 400입니다. 그래서 문법상 올바른 `OPTIONS * HTTP/1.1`이 501이 아니라 400이 됩니다. 리뷰의 `M-SEARCH *` 예는 원래 UDP로 보내는 SSDP 요청이라 이 서버와 상관이 없습니다.

### 방법

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| C1. 지금처럼 400 | 코드 없음. 설계 문서의 "URI는 `/`로 시작" 규칙과 일치 | `OPTIONS *`에 덜 정확한 상태 코드 |
| C2. 메서드와 관계없이 `*` 허용 | 한 줄 | `GET *`도 통과해 `static_resolve_path()`가 `"<root>*"` 경로를 만듦. 파일 이름이 `*`인 파일이 서빙될 수 있음. 위험함 |
| C3. 메서드가 `OPTIONS`일 때만 `*` 허용, 연결 처리가 501 | RFC와 정확히 맞음. 2~3줄 | 지금 단계 범위 밖의 형식을 하나만 따로 추가함 |
| C4. 프록시 단계에서 네 형식을 한꺼번에 설계 | 요청 대상 파싱을 한 번만 다시 설계. 이미 "absolute-form은 프록시 단계"로 제외되어 있음 | 그때까지 `OPTIONS *`는 400 |

### 제안: 지금 C1, 7단계에서 C4 (규칙은 C3)

- 실제 영향이 거의 없습니다. 브라우저와 `curl`이 보내는 일반 요청은 모두 origin-form입니다.
- 7단계 프록시는 absolute-form을 반드시 받아야 하므로 요청 대상 파싱을 그때 다시 짭니다. `*`만 먼저 넣으면 그 설계를 두 번 하게 됩니다.
- 7단계에서 정할 규칙: `*`는 `OPTIONS`에서만 허용하고 다른 메서드면 400. C2처럼 경로 해석에 `*`가 들어가는 일이 없게 연결 처리에서 막습니다.

> 7단계 결과: 리버스 프록시를 택해 위 두 번째 전제(absolute-form)가 사라졌습니다. C1(400)을 유지하고, C3 규칙은 후속으로 미뤘습니다. 후속에서 쓸 규칙은 [리버스 프록시 설계](../reverse-proxy/design.md)를 따릅니다(`OPTIONS *`는 501, `GET *`는 400).
