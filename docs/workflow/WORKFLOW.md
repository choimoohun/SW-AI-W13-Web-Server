# 협업 흐름 (초안 — 팀 합의 전)

- 상태: **초안**. 팀원끼리 정하지 않았으므로 확정 규칙이 아닙니다.
- 기준: 현재 저장소(`SW-AI-W13-Web-Server`)의 `eungi-dev` 브랜치와 PR #18
- 관련 문서: [운영 규칙](./CONVENTIONS.md) · [진행 지도](./PROGRESS.md) · [협업 기록](./COLLABORATION.md) · [검증 로그](../../verify/VERIFICATION_LOG.md)

이 문서는 "나중에 팀과 정할 때 꺼내 쓸 초안"입니다.합의 전에는 제안으로 읽고,
합의된 항목만 상태를 `확정`으로 바꿔서 씁니다.

## 1. 함께 작업할 때

- 서버 코어, 항공편 도메인, 별도 백엔드, 결제는 서로 다른 책임으로 나눕니다.
- 각 작업 단위는 문제 → 설계 → 검증 순서로 적습니다. 설계만 하고 구현하지 않은 것은 완료가 아닙니다.
- 커밋·푸시는 담당자의 요청과 확인을 거칩니다. 자동으로 밀어 넣지 않습니다.
- 커밋 메시지는 `feat: 결제 서비스를 별도 프로세스로 연결`처럼 접두사 뒤에 이해하기 쉬운 한글로 적습니다.
- 서로의 파트를 리뷰할 때는 파일·동작·재현 입력을 지정해 질문합니다. 작성자는 판단 근거와 수정 결과를 답하고, 리뷰어는 재검증 결과를 남깁니다.
- 테스트가 실패하면 실패한 사실을 지우지 않고, 원인 가설과 수정 전후 결과를 함께 남깁니다.
- 다음 단위는 현재 단위의 결과를 확인한 뒤에 시작합니다.

## 2. 채널 규칙

- 알리고 싶은 것, 아이디어, 진행 방식에 대한 의견은 Discussion에 올립니다.
  예: [프로젝트 진행할 때 참고](https://github.com/choimoohun/SW-AI-W13-Web-Server/discussions/2)
- 할 일은 Issue로 올립니다. 논의 중 생긴 할 일도 Issue로 옮깁니다.
  예: [11월 21일 (토)](https://github.com/choimoohun/SW-AI-W13-Web-Server/issues/13) — Discussion #11에서 옮겨 옴
- 코드/문서 변경은 PR로 올리고, 구현한 사람이 무엇을 왜 바꿨는지 설명합니다.
- PR 본문은 `.github/pull_request_template.md`를 씁니다. 한 줄 요약 → 변경 → 이유 → 확인 명령 → 실제 결과 → 남은 것 순서로 짧게 적습니다.
- CodeRabbit은 보조 리뷰어입니다. 자동 코멘트를 참고하되, 제안을 그대로 반영하지 말고 로컬 명령으로 확인합니다.
  - `@coderabbitai review`: 새 커밋 리뷰 요청
  - `@coderabbitai full review`: 파일 전체 다시 리뷰
  - `@coderabbitai pause` / `resume`: 자동 리뷰 중지/재개
  - `@coderabbitai resolve`: CodeRabbit 코멘트 해결 표시
  - 그 외 질문은 `@coderabbitai` 뒤에 자연어로 적음. 명령은 코멘트 하나에 하나씩.
- 리뷰 댓글은 파일·동작·재현 입력을 지정합니다. 작성자는 근거와 수정 결과를 답합니다.

Issue에는 최소한 이걸 적습니다.

```md
### 작업 범위
- [ ] 항목

### 완료 조건
- 무엇이 되면 끝인가

### 검증 명령
- make ...

### 관련 문서/PR
- STEP, DECISIONS, VERIFICATION_LOG 링크
```

Discussion #2에서 정한 진행 방식도 여기에 연결합니다.

```text
- 각자 별도 브랜치에서 작업
- 스크럼에서 작업 범위를 정함
- PR을 올려 각자 구현 설명
- 리뷰로 서로 다른 점을 찾음
- 스크럼 10:30 / 중간 점검 16:00(선택) / 코어 타임 21:00
```

이 내용은 합의된 규칙이라기보다 **참고한 진행 방식**입니다. 팀에서 확정하면 상태를 바꿉니다.

## 3. 브랜치와 저장소 (현재 상태)

```text
작업 브랜치: eungi-dev
원격:        origin git@github.com:choimoohun/SW-AI-W13-Web-Server.git
열린 PR:     #18 (base eungi-main)
```

팀 저장소, 기준 브랜치, 리뷰 승인 인원은 **아직 합의하지 않았습니다.**
합의되면 이 절만 갱신합니다. 개인 브랜치에 푸시했다고 팀 저장소가 바뀌는 것은
아니라는 점을 문서로 남겨 둡니다.

## 4. 기능별 기록 양식

작업할 때마다 아래 항목을 PR 설명이나 작업 기록에 채웁니다. 실행하지 않은
테스트는 `미실행`으로 표시합니다.

```md
### 기능:
- 테스트 목적:
- 기대 동작과 사용 예:
- 설계 선택과 이유:
- 확인할 경계값·실패 조건:
- 실행 환경과 명령:
- 결과(기대/실제):
- 판정(PASS / FAIL / NOT RUN):
- 발견한 문제, 원인 가설, 수정 및 재검증:
- 부하 테스트 조건(입력 규모·동시 연결 수·반복 횟수)과 결과:
- 리뷰 질문·의견과 답변:
- 남은 한계:
```

현재 이 형식에 가장 가까운 기록은 `verify/VERIFICATION_LOG.md`입니다.
부하 테스트는 요청 수·동시성·환경을 함께 적습니다. 성능 수치가 나오기 전에는
빠르다고 주장하지 않습니다.

## 5. 검증 루프

```text
요구사항 확인 → 설계 → 테스트 케이스 → 구현 → 실행 → 실패 기록
→ 원인 수정 → 회귀 검증 → 다음 단위
```

리액트 레포에서 해본 방식과 같은 결입니다. 구현하는 쪽과 검토하는 쪽을 나누고,
고친 범위의 회귀만 다시 돌립니다. 실제로 잡아낸 문제는
[협업 기록](./COLLABORATION.md)의 "검증 루프가 잡아낸 것" 표에 있습니다.

## 6. 문서와 증거의 범위

- 문서는 요약이고, 실제 판정은 실행 기록에 있습니다.
- 이전 대화의 모든 내용을 읽었다고 주장하지 않습니다. 필요하면 세션 기록을 확인합니다.
- 문서 링크·형식 확인과 실제 코드 테스트는 별개로 기록합니다.
- 오래된 결정은 지우지 않고 `당시 …`, `이후 … 완료`로 표시합니다.

## 7. 합의가 필요한 항목

### Discussion #2에서 이미 적힌 참고 방식

- 각자 별도 브랜치를 만들고 그 브랜치에서 작업
- 스크럼에서 작업 범위를 정함 (10:30), 중간 점검 16:00은 선택, 코어 타임 21:00
- PR을 올려 각자 구현을 설명하고 서로 리뷰
- PR 예시: `choimoohun/main ← choimoohun/tcp`

이 방식은 논의에서 나온 참고안입니다. 팀에서 그대로 쓰기로 하면 위에 `확정`을 붙입니다.

### 아직 정하지 않은 것

- 팀 저장소와 기준 브랜치: 현재는 `origin`, `eungi-dev`, PR #18 기준
- 리뷰어와 승인 기준
- 커밋·푸시 타이밍: 현재는 담당자 요청과 확인 후 진행
- 브랜치 네이밍과 머지 방식
- 다음 작업(로그인/세션)의 담당과 순서
