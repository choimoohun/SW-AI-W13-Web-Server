# STEP9 — 별도 백엔드 프로세스 연결

기존에 따로 있던 레포 코드를 C 게이트웨이 뒤에 실제로 연결한 단계입니다.
"같은 바이너리에 다 넣기"와 "별도 프로세스로 두기"의 차이를 시연합니다.

## 1. 연결한 것

| 경로 | 백엔드 | 사용한 코드 |
|---|---|---|
| `/api/cache/*` → `/` | 8000 | `mini-redis-repo/mini_redis/store.py` |
| `/api/stocks/*` → `/` | 8002 | 같은 `Store`를 TTL 캐시로 쓰는 어댑터 |
| `/api/orders/*` → `/` | 8401, 8402 | `why_dbms_demo/app.py`, 역할만 다르게 실행 |
| `/api/payments/*` → `/` | 8500 | STEP10의 결제 서비스 |

`conf/backends.conf`의 `route = prefix|backend...|rewrite` 형식으로 설정합니다.
rewrite는 외부 경로와 백엔드 내부 경로를 분리합니다.
예: `/api/cache/get` → 백엔드의 `/get`.

## 2. 왜 별도 프로세스인가

| 이유 | 시연 방법 |
|---|---|
| 자원 제한 | `ulimit -n`을 64/128/256/512로 다르게 줌 |
| 독립 라이프사이클 | 8401만 죽여도 게이트웨이와 나머지는 생존 |
| 독립 스케일링 | 백엔드 2대에 Round-Robin 분산 |
| 장애 격리 | 죽은 백엔드 경로만 502, `/health`는 200 |

스레드였다면 같은 주소공간이라 파일 디스크립터 한도를 다르게 줄 수 없습니다.

## 3. 게이트웨이 동작

- `proxy.c`가 경로 prefix로 백엔드를 고르고, 여러 대면 Round-Robin합니다.
- `dup()`으로 클라이언트 fd의 소유권을 프록시 큐로 넘깁니다. 워커는 원본을 닫고 바로 이벤트 루프로 돌아갑니다.
- 프록시는 전용 스레드에서 blocking recv를 하므로 느린 백엔드가 워커를 막지 않습니다.
- 연결 실패는 502, 응답 지연은 504로 구분합니다.

## 4. 검증

```sh
make integration-backends
```

실제 결과:

```text
ulimit: 64 / 128 / 256 / 256 / 512
캐시: 404 → 200 → 값 조회
주식: 첫 요청 db, 두 번째 cache
주문: 주문2 / 주문 / 주문2 / 주문
8401 종료 후: 200 502 200 502
8401 재시작 후: 200 200 200 200
/health: 200
```
