# 직접 학습 노트

## 2026-11-23 TCP/IP 스택과 소켓 식별

출처: Chris Kanich 소켓 API 강의와 CSAPP 11.4. 대본 요약은 `study/all-37-materials-detailed.md` 24번(The Linux socket API explained)과 28번(processes, threads, io multiplexing)이다. 관련 링크는 아래 "관련 강의 안내"와 `docs/notes/iomux.md` 참고 자료.

### 1. TCP/IP 스택과 계층

- TCP/IP 스택은 인터넷이 만들어지면서 함께 개발된 프로토콜 스택이다.
- 전송 계층, 인터넷 계층, 물리적 연결 계층은 시스템 계층이다. 시스템 수준에서 구현되고, 앱이 쓸 수 있도록 네트워크 기능을 지원한다.
- 응용 계층은 시스템이 제공하는 네트워크 기능을 사용해서 앱 수준에서 구현한다.
- 앱은 커널 코드를 직접 접근할 수 없다. 다른 앱도 같은 영향을 받기 때문이다. 시스템은 대신 정리된 인터페이스를 제공하고, 앱은 그 인터페이스로 네트워크 기능을 쓴다.
- 그 인터페이스가 소켓이다. 앱은 소켓으로 데이터를 주고받는다.

### 2. 소켓 프로그래밍

- 소켓 프로그래밍: 네트워크 상의 다른 프로세스와 데이터를 주고받도록 구현하는 것. 소켓 인터페이스가 그 도구다.
- 대표 함수: `socket`, `bind`, `listen`, `accept`, `read`, `write`, `close`.
- 대부분의 시스템이 소켓 형태로 네트워크 기능을 제공하므로, 앱은 소켓을 써야만 네트워크 통신을 할 수 있다.
- 실무에서는 앱 계층 프로토콜이 라이브러리나 모듈 형태로 제공되는 경우가 많아서, 개발자가 소켓을 직접 조작하는 일은 적다. 라이브러리 내부를 열어보면 소켓으로 구현돼 있다.

### 3. 포트와 소켓 주소

- 포트는 소켓을 식별하기 위해 부여되는 숫자다. 실제로는 `<protocol, IP address, port number>`로 정의한다.
- `SOCK_STREAM`은 TCP를 의미한다.
- 그 다음 `sockaddr`로 소켓 주소를 부여한다. IP 주소와 포트 번호를 지정한다.
- `bind()`를 호출해서 만든 소켓에 해당 소켓 주소를 묶는다.
- 서버는 포트 번호를 명시해야 클라이언트가 그 포트로 데이터를 볼 수 있다.
- 클라이언트는 명시적으로 `bind()`할 필요가 없다. OS가 알아서 묶어준다.

### 4. TCP 연결과 리스닝 소켓

- TCP는 연결을 맺고 통신한다.
- 서버에는 요청이 들어오는 것을 기다리는 소켓, 즉 리스닝 소켓이 있어야 한다.
- 리스닝 소켓이 연결 요청을 받으면 3방 핸드셰이크를 거쳐 연결이 성립되고, 서버는 별도의 소켓을 만든다.
- 클라이언트는 그 새로 만들어진 소켓과 성립된 연결 위에서 데이터를 주고받는다.
- 인터넷 상의 다른 프로세스가 같은 서버로 접속하면, 같은 순서로 또 다른 소켓이 만들어진다.

### 5. 소켓 식별 문제

- 서버에서 리스닝 소켓과 각 연결 소켓은 로컬 IP·포트가 같을 수 있다.
- 이때 `dest IP`, `dest port`만으로는 어느 소켓으로 보낼지 알 수 없다.
- 그래서 `src IP`, `src port`까지 함께 확인한다. `<src IP, src port, dest IP, dest port>` 4개 값으로 커넥션을 식별한다.
- 클라이언트는 OS가 임시 포트를 자동으로 부여하므로, 같은 서버 포트로 여러 연결을 만들어도 로컬 포트가 달라서 구분된다. 임시 포트가 고갈되면 다른 포트 조합이 쓰일 수 있다.
- UDP는 연결 개념이 없으므로 `<protocol, IP, port>`로 식별한다.

### 6. 우리 구현과의 대조

| 이 노트의 내용 | 우리 코드 | 판단 |
|---|---|---|
| 소켓 인터페이스 `socket/bind/listen/accept/read/write/close` | `src/tcpserver.c:15` `tcpserver_listen`, `src/worker.c:66` `accept`, `src/worker.c:95` `recv`, `src/connection.c` `send`, `src/worker.c:43` `close_conn` | 같음 |
| 서버는 포트를 명시적으로 `bind` | `src/tcpserver.c:43`, 백로그 128 | 같음 |
| 클라이언트는 `bind` 없이 `connect` → OS가 임시 포트 부여 | `src/proxy.c:101,105` (프록시가 백엔드에 연결할 때 `socket` + `connect`, `bind` 없음) | 같음 |
| `SOCK_STREAM`은 TCP | `src/tcpserver.c:27`, `src/proxy.c:91` 모두 `SOCK_STREAM` | 같음 |
| 리스닝 소켓 1개, 연결마다 별도 소켓 | `src/main.c:64`에서 `listen_fd` 하나, `src/worker.c:66` `accept`로 `conn fd` 생성 | 같음 |
| 4-tuple로 커넥션 식별 | 우리 코드가 직접 식별하지 않음. 커널이 4-tuple로 분류해 해당 `fd`로 전달하고, 우리는 `getpeername`으로 클라이언트 IP만 읽어 로그에 씀 (`src/connection.c:79`) | 역할 분담이 다름 |
| UDP 식별 | UDP 미사용 | 해당 없음 |

### 7. 표현 정리

- “소켓이 식별된다”고 말하지 말고 “소켓이 정의된다”고 말하는 편이 정확하다. 소켓은 `<protocol, IP, port>`로 정의하고, 커넥션은 소켓 주소 두 개(4-tuple)로 식별한다.
- “TCP 표준에서는 IP, port가 유니크해야 한다”는 표현은 RFC 793 기준으로 부정확하다. 표준도 커넥션을 소켓 쌍으로 식별한다. 그러므로 “표준과 실제 동작이 다르다”가 아니라, 소켓 주소 단위와 커넥션 식별 단위가 다르다는 표현이 맞다.

## 2026-11-22 발제 노트 (Web-to-MSA)

출처: 발제 자료 `Web-to-MSA-개편.pdf`와 함께 적은 메모. 원문 표현을 그대로 두었다. 용어 사전처럼 읽는다.

### 1. 용어 메모

- 레디스: 공유 인메모리 자료구조. 자료구조 자체가 속도다.
- 트리 vs 컬럼: 왜 둘 다 쓰지 않는가. 컬럼 기반 저장소.
- SQL은 데이터 조작 언어.
- 동시성(CONCURRENT)과 병렬성(PARALLEL)은 다르다.
- `AFFINITY`: 같은 사용자를 같은 서버로 보내는 것.
- 소켓 라이브러리: 네트워크 프로그래밍은 소켓 라이브러리부터.

### 2. 클라이언트-서버 모델

- 클라이언트 서버 중 하나가 웹서버다. 서버에게 데이터를 요청하는 프로그램은 전부 클라이언트다.
- 웹 브라우저는 그 중에서 HTML/CSS/JS를 요청해 화면에 띄우는 전용 클라이언트다.
- 웹서버는 클라이언트-서버 모델 중 하나일 뿐이다.

### 3. 동시성 모델 (발제 발언 그대로)

- `epoll()` with multiprocess (하이브리드) — 좋다.
- multi thread minimum — 스레드는 최소한으로.
- `epoll()` only — 아니다.
- multiprocess only — 아니다.
- 이유는 아래 AI 질의응답 "왜 하이브리드인가"에 정리했다.

### 4. 프록시

- 역사: 아파치만 쓰다가 nginx(`epoll`)로. 동시 접속 10배.
- 웹은 HTTP가 핵심이다. 클라이언트는 웹 브라우저, 서버는 nginx/Envoy를 쓸 수 있다.
- HTTP/1.1이 90%를 차지한다.
- 포워드 프록시: 클라이언트-서버 사이. 보안. 캐시.
- 리버스 프록시: 서버 앞. 라우팅, 캐싱, 로드밸런싱.
- 캐시가 두 개라는 말은 두 계층에서 캐시를 두는 것. 콘텐츠·JS·CSS.

### 5. 네트워크 기초

- 소켓 프로그래밍: 함수를 라인바이라인으로 직접 구현한다.
- 3 way handshake. TCP/UDP. `SO_REUSEADDR`. 블로킹·논블로킹.
- 인터럽트와 논블로킹.
- HTTP 프로토콜 1.1은 웹 프로그래밍 기본.
- 처리량(throughput)과 벤치마크.
- 이벤트 루프.
- 메모리 최적화가 처리량으로 이어진다.
- 멀티 스레드 / 멀티 프로세스.
- inode와 메모리 사용.
- 시그널·종료·그레이스풀 셋업.

### 6. DNS와 포트

- 브라우저는 hosts 파일을 먼저 찾는다.
- 없으면 ISP DNS, 그래도 없으면 8.8.8.8 같은 공개 DNS.
- 도메인은 트리 구조. 루트 서버 → `.com` 담당 → 하위.
- IP만으로는 어플리케이션을 따라갈 수 없다.
- 80은 웹서버, 443은 HTTPS, ssh/dns도 각자 포트가 있다.
- 그 외는 사용자 정의 포트.

### 7. TCP와 UDP

- TCP는 연결을 먼저 맺고 대화한다. 3 way handshake. 순서를 보장하지만 느리다.
- UDP는 실시간 동영상, 음성 통화에 쓰인다. 한두 프레임 손실은 무시하는 편이 낫다.
- HTTP는 그 둘 중 하나를 골라야 한다. 순서와 안정성이 필요하면 TCP, 지연이 더 중요하면 UDP.
- HTML 기준으로는 URL → DNS → IP → TCP 연결 → TLS 순서다.

### 8. HTTP 1.1 / 2 / 3

- HTTP/1.0은 연결을 닫아야 했다.
- 커넥션이 왔다는 것은 소켓이 하나 왔다는 뜻이다. 소켓 구조체와 입출력 버퍼가 필요하다.
- 스레드 구조체. 커넥션이 많아질수록 서버 부하가 커진다. 사용자당 커넥션이 10개면 감당하기 어렵다.
- 크롬은 도메인당 6개를 병렬로 연다.
- HTTP/1.1은 keep-alive로 TCP를 끊지 않는다. 3 way handshake 비용이 줄어든다.
- `Host` 헤더: 한 IP로 여러 도메인을 서빙하기 위해 필요하다.
- HTTP/1.1은 한 연결 안에서 응답이 순서대로만 온다. 앞 응답이 늦으면 뒤도 멈춘다.
- HTTP/2: 메시지를 프레임으로 쪼갠다. 연결 → 스트림 → 메시지 → 프레임. 바이너리 프레이밍, 헤더 압축.
- HTTP/3은 UDP 기반.

### 9. HTTPS와 TLS

- HTTPS가 기본이다. 암호화 계층이 하나 더 있다.
- HTTP는 상태를 유지할 방법이 없다(stateless).

### 10. 세션과 토큰, 쿠키

- 세션은 서버에 저장한다. 키와 값을 해시로.
- 서버가 여러 대면 세션이 공유되지 않는다 → 로그인이 풀린다. 그래서 레디스에 둔다.
- 토큰은 데이터까지 토큰에 담는다.
- 페이지와 페이지 사이를 잇는 것은 쿠키. 요청마다 헤더에 실려 간다.

### 11. CGI와 FastCGI

- 정적 웹: 파일을 그대로 돌려준다.
- CGI: 요청마다 프로그램을 실행한다. 표준 입력으로 데이터를 준다.
- FastCGI: 프로그램을 띄워 두고 재사용한다.
- 인터프리터는 스레드에서 안정성이 떨어진다 → 프로세스.

### 12. 렌더링 방식과 아키텍처

- 서버사이드 렌더링 → ajax → SPA(클라이언트 렌더링).
- 서버가 보내는 것: 완성된 HTML → HTML+데이터 → 빈 HTML+JS 번들+JSON.
- 2티어: 클라이언트가 DB에 직접 붙는다. 배포·보안·확장 문제.
- 3티어: 로직을 서버로 옮긴다.
- 티어는 하드웨어 분리, 레이어는 논리적 분리.

### 13. REST API와 API 게이트웨이

- REST API: 자원, 행위, 표현을 정해 호출을 표준화한다.
- API 게이트웨이: 라우팅, 인증, 트래픽 제어, 관측. 인증을 한 번만 하게 한다.
- L4 스위치: 같은 사용자를 같은 서버로. L7: HTTP를 읽어 처리. URL·헤더·쿠키 기준. 대신 느리다.
- 리버스 프록시가 L7에 해당한다.

### 14. CDN, 캐시, DB

- CDN: 엣지 서버에서 캐시한다.
- 레디스에 먼저 넣어 두고 주기적으로 DB에서 가져오는 방식도 있다.
- DB 확장: 읽기 전용 DB를 빼고, 쓰기 전용과 동기화 시점을 고민한다.

### 15. MSA

- MSA는 하나의 애플리케이션에 상품·주문이 다 있고 하나의 DB를 쓰는 구조를 서비스별로 나눈다.
- 커뮤니케이션 비용이 든다. 대신 독립 배포, 기술 선택, 조직 확장이 가능하다.
- 경계가 명확하고 회사 확장성이 보장될 때 어울린다.

# AI 질의응답

## 2026-11-23 블로킹/논블로킹, 멀티플렉싱, 이벤트 루프와 스레드 풀

### 1. 블로킹과 논블로킹 시스템 콜

- 블로킹: 데이터가 준비되지 않으면 스레드가 블록된다. 커널은 스레드를 대기 상태로 바꾸고 CPU를 회수한다. 데이터가 도착하면 스레드가 깨어난다.
- 논블로킹: 준비되지 않았으면 즉시 `-1`과 `EAGAIN`/`EWOULDBLOCK`을 돌려준다. 스레드는 다른 코드를 계속 실행할 수 있다.
- 소켓에는 수신 버퍼와 송신 버퍼 두 개가 있다(커널). 앱도 `connection_t`에 `recv_buf`/`send_buf`를 따로 두고 있다.
- `read`는 수신 버퍼에 데이터가 없으면 “없다”고 알려주고 반환이 끝난다(논블로킹). `write`는 송신 버퍼가 가득 차면 블로킹에서는 비워질 때까지 블록, 논블로킹에서는 에러 코드와 함께 반환된다.
- 우리 구현: `accept()`로 받은 fd를 `O_NONBLOCK`으로 바꾸고(`src/worker.c:72`), `recv`는 `EAGAIN`이면 다음 fd로(`src/worker.c:105`), `send`는 `EAGAIN`이면 `WRITE` 관심을 유지(`src/connection.c:304`).

### 2. 논블로킹에서 “완료”를 확인하는 방법

- 반복 확인(busy polling): 완료됐는지 계속 물어본다. CPU 사이클 낭비.
- 멀티플렉싱: `select`/`poll`/`epoll`/`kqueue`/`IOCP`. 한 번의 시스템 콜로 여러 fd를 감시하고 준비된 것만 알려준다.
- 비동기 I/O: POSIX AIO, Linux AIO, `io_uring`. 커널이 작업을 시작하고 스레드는 독립적으로 실행, 완료는 콜백/시그널로 알린다.

### 3. 멀티플렉싱과 이벤트 루프

- 멀티플렉싱: 커널이 “지금 준비된 fd가 누구냐”를 알려주는 수단.
- 이벤트 루프: `wait → 준비된 fd 처리 → 다시 wait`를 반복하는 실행 모델.
- `epoll_wait`은 관심 fd 중 하나라도 준비되면 즉시 돌아온다. 전부 준비될 때까지 기다리지 않는다. 우리는 타임아웃 200ms를 둬서 유휴 정리도 한다(`src/worker.c:25,161`).

### 4. 이벤트 루프 + 멀티플렉싱 vs 스레드 풀 + 멀티플렉싱

- 이 둘은 서로 대체 관계가 아니라 다른 축이다.
  - 멀티플렉싱: 커널 I/O 통지 수단.
  - 이벤트 루프: 그 알림을 받아 처리하는 실행 모델.
  - 스레드 풀: 그 실행 모델을 몇 개 둘 것인가.
- 조합의 예:
  - 단일 스레드 이벤트 루프 + 멀티플렉싱: Node.js, Redis. 코어 1개.
  - 멀티 스레드 이벤트 루프 + 멀티플렉싱: 우리 서버. 워커 4개가 각자 `iomux`를 들고 돈다.
  - 스레드 풀 + 블로킹 I/O: 전통적 스레드 풀. 멀티플렉싱 없음.
  - 멀티플렉서 + 워커 풀: 선택자가 이벤트를 받아 작업을 풀에 분배(Netty boss/worker, Envoy).
- “스레드 풀 + 멀티플렉싱”이 “이벤트 루프 + 멀티플렉싱”과 다른지 여부는 스레드 풀이 어떤 일을 하냐에 따라 다르다. 스레드 풀의 각 스레드가 이벤트 루프를 돌리면 우리 구조와 같고, 블로킹 작업을 받아 처리하면 전통적 워커 풀과 같다.

### 5. 우리 구현에서의 위치

- `worker_pool_start()`가 워커 4개를 만든다(스레드 풀, `src/worker.c:207`).
- 각 워커는 `iomux_create()`로 자기 `epoll`/`kqueue`를 만들고(`src/worker.c:152`), `listen fd`를 자기 `iomux`에 등록한다(`src/worker.c:154`).
- 이후 `while` 루프가 `iomux_wait()` → 이벤트 처리 → `cleanup_idle()`을 반복한다(이벤트 루프, `src/worker.c:160-184`).
- 즉 우리는 스레드 풀 + 멀티플렉싱 + 각 스레드의 이벤트 루프를 같이 쓴다.
- `listen fd`는 4개 워커가 공유하므로 `accept` 경쟁이 생긴다. 한 이벤트당 1건만 `accept()`하고, 나머지는 `EAGAIN`으로 스킵한다(`src/worker.c:57-59,66`). `accept`로 나온 `conn fd`는 그 워커가 끝까지 소유한다.

### 6. 표현 정리

- `IOCP`는 Windows의 I/O 완료 포트다. Solaris는 event ports(`/dev/poll`)를 쓴다.
- `select`/`poll`은 관심 fd 전체를 훑어 O(n). `epoll`/`kqueue`는 준비된 것만 돌려줘 O(준비 수).
- “스레드 풀이 무조건 이벤트 루프보다 낫다/나쁘다”가 아니라, 실행 주체 수(스레드)와 대기 방식(블로킹/멀티플렉싱)은 별개로 결정한다.

### 7. `epoll_wait`이 깨어난 스레드는 무엇을 받는가

- 앱의 “작업 큐”가 따로 있는 게 아니다. 커널의 `epoll` 준비 목록에서 `epoll_wait()`가 준비된 fd 배열을 돌려준다(`src/iomux.c:330-341`).
- 돌려받은 배열을 워커가 `for`문으로 순서대로 처리한다(`src/worker.c:166-176`). 알림은 이 배열 하나뿐이고, 별도 전달 단계는 없다.
- “3개 소켓에 데이터가 있다”는 것은 배열에 3개의 이벤트가 담겨 있다는 뜻이다. 워커는 그 3개만 처리한다.

## 2026-11-23 HTTP에 메시지 큐를 추가하는가

- 질문: HTTP에 메시지 큐를 추가하는가?
- 답변: 안 한다. 요구사항(`docs/REQUIREMENTS.md` FR-01~08, NFR-01~04)에는 메시지 큐 항목이 없다. 지금 구조는 동기 HTTP + 프록시 전용 스레드로 백엔드 지연을 격리하는 정도다.
- 메시지 큐를 도입하려면 `202 Accepted + job_id` 응답, 별도 워커, 완료 알림(폴링/웹훅/SSE)이 필요한데 이번 범위를 넘는다.
- 메시지 큐가 푸는 문제는 “느린 서버와의 커플링·백프레셔”이지, HTTP/1.1의 HOL blocking이 아니다. 둘을 같은 문제로 보지 않는다.

## 2026-11-23 HTTP/1.1 슬로우 스타트

- 질문: HTTP/1.1에서 처음 연결할 때 슬로우 스타트가 일어나는데, 이걸 극복하려면 어떻게 개선하는가?
- 원인: 슬로우 스타트는 TCP 혼잡 제어의 일부다. 새 연결의 혼잡 윈도우(`cwnd`)가 작게 시작해서 점진적으로 늘어나므로, 연결 직후의 전송 속도가 낮다. 혼잡 붕괴를 막기 위한 동작이라 끌 수 없다.
- 그래서 “극복”이 아니라 “영향을 줄이는” 방향이 맞다.
- 줄이는 방법:
  - 연결 재사용(keep-alive): 매 요청마다 새 연결을 맺지 않으면 슬로우 스타트도 한 번만 든다. 우리 서버는 keep-alive을 최대 100회까지 허용한다.
  - 초기 혼잡 윈도우 키우기: Linux `net.ipv4.tcp_initcwnd`나 경로의 `initcwnd` 값. RFC 6928은 초기 윈도우 10 MSS를 권고한다.
  - `net.ipv4.tcp_slow_start_after_idle=0`: 유휴 연결이 다시 데이터를 보낼 때 슬로우 스타트로 돌아가는 것을 방지한다.
  - TCP Fast Open(TFO): 첫 데이터를 핸드셰이크와 함께 보낸다.
  - HTTP/2 또는 HTTP/3(QUIC): 한 연결에서 여러 요청을 멀티플렉싱하고, HTTP/3는 0-RTT로 첫 전송을 앞당긴다.
  - 브라우저가 도메인당 여러 연결(보통 6개)을 여는 것, CDN·지리적으로 가까운 서버, 압축, 첫 바이트까지의 시간 단축.
- 우리 프로젝트에서 지금 할 수 있는 것은 keep-alive(이미 적용)와 첫 응답 최적화 정도다. TCP 튜닝은 OS/커널 설정이라 앱 코드 밖이고, HTTP/2·HTTP/3은 요구사항에 없어 범위 밖이다.

## 2026-11-22 왜 `epoll` + 멀티프로세스(하이브리드)인가

- 질문: 발제에서 `epoll()` with multiprocess(하이브리드)가 좋고, multi thread minimum, `epoll()` only 아니고, multiprocess only 아니라고 했다. 이유가 뭔가?
- 답변:
  - `epoll` only(단일 프로세스 단일 스레드 이벤트 루프): 코어를 하나밖에 못 쓴다. 요청 처리가 길어지면 프로세스 전체가 막힌다. 동시 연결은 잘 처리하지만 CPU 집중 작업에 약하다.
  - multiprocess only(블로킹 멀티프로세스): 프로세스 수만큼 메모리와 컨텍스트 스위치 비용이 든다. 연결마다 프로세스를 띄우면 동시 접속이 늘 때 무겁다. 공유 상태(좌석)도 프로세스 간 공유가 어렵다.
  - 멀티스레드: 프로세스보다 가볍지만 같은 주소공간이라 동기화가 필요하고, 한 스레드의 크래시가 전체를 죽인다. 그래서 "minimum"이라 했을 것이다.
  - 하이브리드: 프로세스를 코어 수만큼 띄우고, 각자가 `epoll` 이벤트 루프를 돈다. 코어를 다 쓰고 프로세스 격리도 얻고, 블로킹 멀티프로세스보다 가볍다. nginx와 Envoy가 이 구조다.
  - 우리 선택은 프로세스 대신 스레드. 이유는 좌석 공유 비용(공유 메모리·IPC가 필요). 대가는 크래시 격리 부재.

## 2026-11-22 CGI/FastCGI, Next.js·SSG·SOA·REST API는 범위인가

- 질문: fastcgi가 결국 스레드 풀인가? cgi가 매번 재사용인가? next.js, ssg, soa, restapi는 이번 과제 범위인가?
- 답변:
  - CGI: 요청마다 프로세스를 실행한다. 매번 새로 만들고 종료한다. 재사용이 아니다. 질문의 "cgi가 매번 재사용"은 반대다.
  - FastCGI: 프로그램(프로세스)을 띄워 두고 요청을 재사용한다. 스레드 풀과 비슷한 효과를 프로세스로 얻는 방식이다.
  - 우리 프로젝트: FR-05에서 안 A(CGI)를 버리고 안 B(내장 동적 핸들러 + 백엔드 프록시)를 골랐다. FastCGI도 범위 밖이다.
  - Next.js/SSG: 프레임워크다. 우리는 C로 직접 만드는 것이 목표라 범위 밖이다.
  - SOA/REST API: 개념은 관통한다. `/api/...`가 REST 스타일이고, 프록시 모듈이 게이트웨이의 일부 역할을 한다. 다만 프레임워크를 쓰지는 않는다.

## 2026-11-22 직렬화, `send_all`, 청크 전송 용어

- 질문: 직렬화, `send_all`, 청크 전송처럼 실무에서 다 아는 용어인지 확인해 달라.
- 답변:
  - 직렬화: 구조체·객체를 바이트열로 바꾸는 것. JSON, protobuf가 직렬화 형식이다. 우리 `http_response_build_*()`가 문자열을 버퍼에 순서대로 나열하는 것도 직렬화에 해당한다. 실무 용어 맞다.
  - `send_all`: POSIX 표준 함수는 아니다. `send()`가 부분 쓰기(short write)를 할 수 있어서 "남은 바이트를 계속 보내는 루프"를 흔히 그렇게 부른다. 설명할 때는 "partial write 처리"가 더 정확하다.
  - 청크 전송: HTTP `Transfer-Encoding: chunked`의 번역이다. 실무 용어 맞다. 다만 우리 문서에서 "파일을 16KB 단위로 나눠 본내는 것"을 청크 전송이라고 쓴다. HTTP의 chunked 인코딩과는 다른 의미이므로 문서에서 구분을 명시해야 한다.

### 원문 (오기 포함)

프로세스는 각 작업을 격리하고 싶을때 메모리 공유 유용하거나 여러 프로세스 사용하여 병렬로 처리하는 것이 유리할 때 매우 작은 작업 수행하는 수많은 클랑이너트 있을때 CPU 작업량은 많지 않지미나 다양한 작업을 처리하는 웹 서버 실행이나 gui 상호작용수신과 같은 경우 웹서버는 전세계 클라이언트로부터 요청을 받고 중단없이 각 요청을 수행하는 것임. 최대한 빠르게 진행하고 다음으로 넘어가고. 다양한 연결을 추적하고, 운영체제가 스레드를 선점하는 대신 한 작업을 완료한 후 다른 스레드를 시작하여 작업을 마무리하도록 도와주는 것임. 불필요한 스와핑이 줄고 성능이 향상되지만 직접 코드를 작서애향ㄷ 함. 복잡한 락킹이 필요하지 않을 때는 유용함. 스레드들이 긴밀하게 협력하고 모두 동일한 작업을 수행하지만 동일 한 공유 자료구조를 사용해야 할 때는 반드시 사용할 필요는 없음. 또 다른 구성요소는 항상 개별 스레드의 제어 하에 이루어진다는 것이다. 4개 CPU 사용하여 4배 더 많은 요청을 처리해야 함. 네개의 서로 다른 프로세스 포크하고 각 프로세스가 동일하 ㄴ소켓에서 동시에 연결을 수락하고 각 프로세스에서 독립적으로 처리하도록 함. 프로세스라는 두가지 요소를 결합하면 격리성이 향상되고 IO 멀티플렉싱을 통해서성능이 향상됨. 이 둘을 통해 초당 수백 수천 수십만 개의 연결을 처리하는 효율 적인 웹 서버 프레임워크를 구성할 수 잇음. 이러한 개별 작업들이 서로 완전히 독립적이라는 점임. 작업 완룔르 위해 복잡한 조정이 필요하지 않음. 또한 작업 간 격리가 필요하지 않ㄴ음. 하나의 데이터 구조에 저장되어있고, 하나의 프로세스에 저장되므로, 요청 간 격리가 없음. 이들이 서로 상호작용하여 예상치 못한 무너다 발생하면 오류에 노출이 됨. IO 멀티 플렉싱기반 코딩 방식을 사용할때 이러한 연결 간의 격리가 거의 일어나지 않음.

### 정리 — 프로세스 / 스레드 / IO 멀티플렉싱

- 프로세스: 작업을 격리하고 싶을 때. 메모리 공유가 필요하거나 여러 프로세스로 병렬 처리하는 게 유리할 때.
- 스레드: 수많은 클라이언트가 매우 작은 작업을 요청할 때. CPU 작업량은 많지 않지만 다양한 작업을 처리하는 웹 서버, GUI 상호작용 수신 같은 경우.
- 웹 서버: 전 세계 클라이언트의 요청을 중단 없이 받는다. 최대한 빠르게 처리하고 다음으로 넘어간다.
- OS 선점 대신 협력적 실행: 한 작업을 완료한 뒤 다른 작업을 시작한다. 불필요한 스와핑이 줄고 성능은 좋아지지만, 직접 코드를 작성해야 하고 복잡한 락킹이 필요 없을 때 유리하다.
- 스레드가 같은 공유 자료구조를 써야 할 때는 반드시 스레드가 필요한 건 아니다.
- 개별 스레드의 제어 하에 실행된다(선점형이 아니라 프로그래머가 제어).
- 4 CPU → 4배 처리: 4개의 프로세스를 `fork()`해 같은 소켓에서 동시에 `accept()`. 격리(프로세스) + IO 멀티플렉싱(성능) 결합 → 초당 수백~수십만 연결.
- 작업이 완전히 독립적이면 복잡한 조정이 필요 없고, 작업 간 격리도 필요 없다.
- 스레드 모델: 하나의 데이터 구조를 하나의 프로세스에 두므로 요청 간 격리가 없다. 요청이 서로 상호작용해 예상치 못한 문제가 생기면 오류에 노출된다.

### 마지막 문장 해석

> IO 멀티플렉싱 기반 코딩 방식을 사용할 때 이러한 연결 간의 격리가 거의 일어나지 않음.

앞의 “스레드는 요청 간 격리가 없다”와 대비되는 말이다. 두 가지로 읽을 수 있다.

1. **격리가 없다**: 한 스레드가 여러 연결을 같이 처리하므로 프로세스처럼 연결이 서로 격리되어 있지 않다. 격리의 이점은 없지만, 한 번에 하나의 연결만 처리하므로 스레드처럼 두 요청이 동시에 공유 자료구조를 건드려 생기는 예상치 못한 상호작용(경쟁 조건)도 없다.
2. **간섭이 없다**: “격리”가 “간섭”의 오기일 가능성. 한 스레드가 순차적으로 처리하므로 연결 간 간섭이 거의 없다.

어느 쪽이든 핵심은 “IO 멀티플렉싱은 한 스레드가 여러 연결을 같이 돌리므로, 공유 자료구조를 두 요청이 동시에 건드리는 일이 없다”는 것이다. 이것이 우리 프로젝트에서 `flight_store`의 좌석 배열을 `pthread_mutex`로 보호하면서도 연결 처리 자체는 스레드 경쟁 없이 돌리는 이유와 맞닿아 있다.

### 관련 정의 — 동시성

같은 주제에서 “동시성이란 여러 프로세스가 실행될 때 모두 같은 프로세스를 사용하더라도 모두 인터리빙하는 현상”이라고 한 부분. 이것도 오기로 보인다.

- “여러 프로세스가 실행될 때” → “여러 스레드(또는 여러 작업)가 실행될 때”가 맞다.
- 정정하면: **동시성은 여러 작업이 같은 시간대에 진행되는 현상이다. 같은 프로세스(메모리)를 공유하더라도 작업들이 인터리빙(번갈아 실행)한다.**
- 동시성이 꼭 여러 프로세스를 필요로 하지 않는다. 한 프로세스 안의 여러 스레드, 심지어 스레드 하나가 IO 멀티플렉싱으로 여러 연결을 번갈아 처리하는 경우도 동시성이다.
- 우리 서버는 `main.c`가 프로세스 1개를 만들고 `worker_pool_start()`가 스레드를 N개 띄운다. 즉 동시성을 “하나의 프로세스 + 여러 스레드”로 만든다. 강의의 정의가 틀린 게 아니라 대본의 “프로세스”가 “스레드”여야 한다.
- 동시성(concurrency)과 병렬성(parallelism)은 다르다. 병렬성은 여러 작업이 같은 순간에 실제로 실행되는 것(멀티코어 필요). 동시성은 겹치는 시간대에 진행되는 것(인터리빙 포함).
