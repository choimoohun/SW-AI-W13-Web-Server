# 직접 학습 노트

## 2026-11-23 TCP/IP 스택과 소켓 식별

출처: Chris Kanich 소켓 API 강의와 CSAPP 11.4. 대본 요약은 `docs/notes/all-37-materials-detailed.md` 24번(The Linux socket API explained)과 28번(processes, threads, io multiplexing)이다. 관련 링크는 아래 "관련 강의 안내"와 `docs/notes/iomux.md` 참고 자료.

### 1. TCP/IP 스택과 계층

- TCP/IP 스택은 인터넷이 만들어지면서 함께 개발된 프로토콜 스택이다.
- 전송 계층, 인터넷 계층, 물리적 연결 계층은 시스템 계층이다. 시스템 수준에서 구현되고, 앱이 쓸 수 있도록 네트워크 기능을 지원한다.
- 응용 계층은 시스템이 제공하는 네트워크 기능을 사용해서 앱 수준에서 구현한다.
- 앱은 커널 코드를 직접 접근할 수 없다. 다른 앱도 같은 영향을 받기 때문이다. 시스템은 대신 정리된 인터페이스를 제공하고, 앱은 그 인터페이스로 네트워크 기능을 쓴다.
- 그 인터페이스가 소켓이다. 앱은 소켓으로 데이터를 주고받는다.

### 2. 소켓 프로그래밍

- 소켓 프로그래밍: 네트워크 상의 다른 프로세스와 데이터를 주고받도록 구현하는 것. 소켓 인터페이스가 그 도구다.
- 대표 함수: `socket`, `bind`, `listen`, `accept`, `read`, `write`, `close`.
- 대부분의 시스템이 소켓 형태로 네트워크 기능을 제공하므로, 앱은 소켓을 써야만 네트워크 통신을 할 수 있다.
- 실무에서는 앱 계층 프로토콜이 라이브러리나 모듈 형태로 제공되는 경우가 많아서, 개발자가 소켓을 직접 조작하는 일은 적다. 라이브러리 내부를 열어보면 소켓으로 구현돼 있다.

### 3. 포트와 소켓 주소

- 포트는 소켓을 식별하기 위해 부여되는 숫자다. 실제로는 `<protocol, IP address, port number>`로 정의한다.
- `SOCK_STREAM`은 TCP를 의미한다.
- 그 다음 `sockaddr`로 소켓 주소를 부여한다. IP 주소와 포트 번호를 지정한다.
- `bind()`를 호출해서 만든 소켓에 해당 소켓 주소를 묶는다.
- 서버는 포트 번호를 명시해야 클라이언트가 그 포트로 데이터를 볼 수 있다.
- 클라이언트는 명시적으로 `bind()`할 필요가 없다. OS가 알아서 묶어준다.

### 4. TCP 연결과 리스닝 소켓

- TCP는 연결을 맺고 통신한다.
- 서버에는 요청이 들어오는 것을 기다리는 소켓, 즉 리스닝 소켓이 있어야 한다.
- 리스닝 소켓이 연결 요청을 받으면 3방 핸드셰이크를 거쳐 연결이 성립되고, 서버는 별도의 소켓을 만든다.
- 클라이언트는 그 새로 만들어진 소켓과 성립된 연결 위에서 데이터를 주고받는다.
- 인터넷 상의 다른 프로세스가 같은 서버로 접속하면, 같은 순서로 또 다른 소켓이 만들어진다.

### 5. 소켓 식별 문제

- 서버에서 리스닝 소켓과 각 연결 소켓은 로컬 IP·포트가 같을 수 있다.
- 이때 `dest IP`, `dest port`만으로는 어느 소켓으로 보낼지 알 수 없다.
- 그래서 `src IP`, `src port`까지 함께 확인한다. `<src IP, src port, dest IP, dest port>` 4개 값으로 커넥션을 식별한다.
- 클라이언트는 OS가 임시 포트를 자동으로 부여하므로, 같은 서버 포트로 여러 연결을 만들어도 로컬 포트가 달라서 구분된다. 임시 포트가 고갈되면 다른 포트 조합이 쓰일 수 있다.
- UDP는 연결 개념이 없으므로 `<protocol, IP, port>`로 식별한다.

### 6. 우리 구현과의 대조

| 이 노트의 내용 | 우리 코드 | 판단 |
|---|---|---|
| 소켓 인터페이스 `socket/bind/listen/accept/read/write/close` | `src/tcpserver.c:15` `tcpserver_listen`, `src/worker.c:66` `accept`, `src/worker.c:95` `recv`, `src/connection.c` `send`, `src/worker.c:43` `close_conn` | 같음 |
| 서버는 포트를 명시적으로 `bind` | `src/tcpserver.c:43`, 백로그 128 | 같음 |
| 클라이언트는 `bind` 없이 `connect` → OS가 임시 포트 부여 | `src/proxy.c:101,105` (프록시가 백엔드에 연결할 때 `socket` + `connect`, `bind` 없음) | 같음 |
| `SOCK_STREAM`은 TCP | `src/tcpserver.c:27`, `src/proxy.c:91` 모두 `SOCK_STREAM` | 같음 |
| 리스닝 소켓 1개, 연결마다 별도 소켓 | `src/main.c:64`에서 `listen_fd` 하나, `src/worker.c:66` `accept`로 `conn fd` 생성 | 같음 |
| 4-tuple로 커넥션 식별 | 우리 코드가 직접 식별하지 않음. 커널이 4-tuple로 분류해 해당 `fd`로 전달하고, 우리는 `getpeername`으로 클라이언트 IP만 읽어 로그에 씀 (`src/connection.c:79`) | 역할 분담이 다름 |
| UDP 식별 | UDP 미사용 | 해당 없음 |

### 7. 표현 정리

- “소켓이 식별된다”고 말하지 말고 “소켓이 정의된다”고 말하는 편이 정확하다. 소켓은 `<protocol, IP, port>`로 정의하고, 커넥션은 소켓 주소 두 개(4-tuple)로 식별한다.
- “TCP 표준에서는 IP, port가 유니크해야 한다”는 표현은 RFC 793 기준으로 부정확하다. 표준도 커넥션을 소켓 쌍으로 식별한다. 그러므로 “표준과 실제 동작이 다르다”가 아니라, 소켓 주소 단위와 커넥션 식별 단위가 다르다는 표현이 맞다.

## 2026-11-22 발제 노트 (Web-to-MSA)

출처: 발제 자료 `Web-to-MSA-개편.pdf`와 함께 적은 메모. 원문 표현을 그대로 두었다. 용어 사전처럼 읽는다.

### 1. 용어 메모

- 레디스: 공유 인메모리 자료구조. 자료구조 자체가 속도다.
- 트리 vs 컬럼: 왜 둘 다 쓰지 않는가. 컬럼 기반 저장소.
- SQL은 데이터 조작 언어.
- 동시성(CONCURRENT)과 병렬성(PARALLEL)은 다르다.
- `AFFINITY`: 같은 사용자를 같은 서버로 보내는 것.
- 소켓 라이브러리: 네트워크 프로그래밍은 소켓 라이브러리부터.

### 2. 클라이언트-서버 모델

- 클라이언트 서버 중 하나가 웹서버다. 서버에게 데이터를 요청하는 프로그램은 전부 클라이언트다.
- 웹 브라우저는 그 중에서 HTML/CSS/JS를 요청해 화면에 띄우는 전용 클라이언트다.
- 웹서버는 클라이언트-서버 모델 중 하나일 뿐이다.

### 3. 동시성 모델 (발제 발언 그대로)

- `epoll()` with multiprocess (하이브리드) — 좋다.
- multi thread minimum — 스레드는 최소한으로.
- `epoll()` only — 아니다.
- multiprocess only — 아니다.
- 이유는 아래 AI 질의응답 "왜 하이브리드인가"에 정리했다.

### 4. 프록시

- 역사: 아파치만 쓰다가 nginx(`epoll`)로. 동시 접속 10배.
- 웹은 HTTP가 핵심이다. 클라이언트는 웹 브라우저, 서버는 nginx/Envoy를 쓸 수 있다.
- HTTP/1.1이 90%를 차지한다.
- 포워드 프록시: 클라이언트-서버 사이. 보안. 캐시.
- 리버스 프록시: 서버 앞. 라우팅, 캐싱, 로드밸런싱.
- 캐시가 두 개라는 말은 두 계층에서 캐시를 두는 것. 콘텐츠·JS·CSS.

### 5. 네트워크 기초

- 소켓 프로그래밍: 함수를 라인바이라인으로 직접 구현한다.
- 3 way handshake. TCP/UDP. `SO_REUSEADDR`. 블로킹·논블로킹.
- 인터럽트와 논블로킹.
- HTTP 프로토콜 1.1은 웹 프로그래밍 기본.
- 처리량(throughput)과 벤치마크.
- 이벤트 루프.
- 메모리 최적화가 처리량으로 이어진다.
- 멀티 스레드 / 멀티 프로세스.
- inode와 메모리 사용.
- 시그널·종료·그레이스풀 셋업.

### 6. DNS와 포트

- 브라우저는 hosts 파일을 먼저 찾는다.
- 없으면 ISP DNS, 그래도 없으면 8.8.8.8 같은 공개 DNS.
- 도메인은 트리 구조. 루트 서버 → `.com` 담당 → 하위.
- IP만으로는 어플리케이션을 따라갈 수 없다.
- 80은 웹서버, 443은 HTTPS, ssh/dns도 각자 포트가 있다.
- 그 외는 사용자 정의 포트.

### 7. TCP와 UDP

- TCP는 연결을 먼저 맺고 대화한다. 3 way handshake. 순서를 보장하지만 느리다.
- UDP는 실시간 동영상, 음성 통화에 쓰인다. 한두 프레임 손실은 무시하는 편이 낫다.
- HTTP는 그 둘 중 하나를 골라야 한다. 순서와 안정성이 필요하면 TCP, 지연이 더 중요하면 UDP.
- HTML 기준으로는 URL → DNS → IP → TCP 연결 → TLS 순서다.

### 8. HTTP 1.1 / 2 / 3

- HTTP/1.0은 연결을 닫아야 했다.
- 커넥션이 왔다는 것은 소켓이 하나 왔다는 뜻이다. 소켓 구조체와 입출력 버퍼가 필요하다.
- 스레드 구조체. 커넥션이 많아질수록 서버 부하가 커진다. 사용자당 커넥션이 10개면 감당하기 어렵다.
- 크롬은 도메인당 6개를 병렬로 연다.
- HTTP/1.1은 keep-alive로 TCP를 끊지 않는다. 3 way handshake 비용이 줄어든다.
- `Host` 헤더: 한 IP로 여러 도메인을 서빙하기 위해 필요하다.
- HTTP/1.1은 한 연결 안에서 응답이 순서대로만 온다. 앞 응답이 늦으면 뒤도 멈춘다.
- HTTP/2: 메시지를 프레임으로 쪼갠다. 연결 → 스트림 → 메시지 → 프레임. 바이너리 프레이밍, 헤더 압축.
- HTTP/3은 UDP 기반.

### 9. HTTPS와 TLS

- HTTPS가 기본이다. 암호화 계층이 하나 더 있다.
- HTTP는 상태를 유지할 방법이 없다(stateless).

### 10. 세션과 토큰, 쿠키

- 세션은 서버에 저장한다. 키와 값을 해시로.
- 서버가 여러 대면 세션이 공유되지 않는다 → 로그인이 풀린다. 그래서 레디스에 둔다.
- 토큰은 데이터까지 토큰에 담는다.
- 페이지와 페이지 사이를 잇는 것은 쿠키. 요청마다 헤더에 실려 간다.

### 11. CGI와 FastCGI

- 정적 웹: 파일을 그대로 돌려준다.
- CGI: 요청마다 프로그램을 실행한다. 표준 입력으로 데이터를 준다.
- FastCGI: 프로그램을 띄워 두고 재사용한다.
- 인터프리터는 스레드에서 안정성이 떨어진다 → 프로세스.

### 12. 렌더링 방식과 아키텍처

- 서버사이드 렌더링 → ajax → SPA(클라이언트 렌더링).
- 서버가 보내는 것: 완성된 HTML → HTML+데이터 → 빈 HTML+JS 번들+JSON.
- 2티어: 클라이언트가 DB에 직접 붙는다. 배포·보안·확장 문제.
- 3티어: 로직을 서버로 옮긴다.
- 티어는 하드웨어 분리, 레이어는 논리적 분리.

### 13. REST API와 API 게이트웨이

- REST API: 자원, 행위, 표현을 정해 호출을 표준화한다.
- API 게이트웨이: 라우팅, 인증, 트래픽 제어, 관측. 인증을 한 번만 하게 한다.
- L4 스위치: 같은 사용자를 같은 서버로. L7: HTTP를 읽어 처리. URL·헤더·쿠키 기준. 대신 느리다.
- 리버스 프록시가 L7에 해당한다.

### 14. CDN, 캐시, DB

- CDN: 엣지 서버에서 캐시한다.
- 레디스에 먼저 넣어 두고 주기적으로 DB에서 가져오는 방식도 있다.
- DB 확장: 읽기 전용 DB를 빼고, 쓰기 전용과 동기화 시점을 고민한다.

### 15. MSA

- MSA는 하나의 애플리케이션에 상품·주문이 다 있고 하나의 DB를 쓰는 구조를 서비스별로 나눈다.
- 커뮤니케이션 비용이 든다. 대신 독립 배포, 기술 선택, 조직 확장이 가능하다.
- 경계가 명확하고 회사 확장성이 보장될 때 어울린다.

IO 멀티 플렉싱기반 코딩 방식을 사용할때 이러한 연결 간의 격리가 거의 일어나지 않음.

### 정리 — 프로세스 / 스레드 / IO 멀티플렉싱

- 프로세스: 작업을 격리하고 싶을 때. 메모리 공유가 필요하거나 여러 프로세스로 병렬 처리하는 게 유리할 때.
- 스레드: 수많은 클라이언트가 매우 작은 작업을 요청할 때. CPU 작업량은 많지 않지만 다양한 작업을 처리하는 웹 서버, GUI 상호작용 수신 같은 경우.
- 웹 서버: 전 세계 클라이언트의 요청을 중단 없이 받는다. 최대한 빠르게 처리하고 다음으로 넘어간다.
- OS 선점 대신 협력적 실행: 한 작업을 완료한 뒤 다른 작업을 시작한다. 불필요한 스와핑이 줄고 성능은 좋아지지만, 직접 코드를 작성해야 하고 복잡한 락킹이 필요 없을 때 유리하다.
- 스레드가 같은 공유 자료구조를 써야 할 때는 반드시 스레드가 필요한 건 아니다.
- 개별 스레드의 제어 하에 실행된다(선점형이 아니라 프로그래머가 제어).
- 4 CPU → 4배 처리: 4개의 프로세스를 `fork()`해 같은 소켓에서 동시에 `accept()`. 격리(프로세스) + IO 멀티플렉싱(성능) 결합 → 초당 수백~수십만 연결.
- 작업이 완전히 독립적이면 복잡한 조정이 필요 없고, 작업 간 격리도 필요 없다.
- 스레드 모델: 하나의 데이터 구조를 하나의 프로세스에 두므로 요청 간 격리가 없다. 요청이 서로 상호작용해 예상치 못한 문제가 생기면 오류에 노출된다.

### 마지막 문장 해석

> IO 멀티플렉싱 기반 코딩 방식을 사용할 때 이러한 연결 간의 격리가 거의 일어나지 않음.

앞의 “스레드는 요청 간 격리가 없다”와 대비되는 말이다. 두 가지로 읽을 수 있다.

1. **격리가 없다**: 한 스레드가 여러 연결을 같이 처리하므로 프로세스처럼 연결이 서로 격리되어 있지 않다. 격리의 이점은 없지만, 한 번에 하나의 연결만 처리하므로 스레드처럼 두 요청이 동시에 공유 자료구조를 건드려 생기는 예상치 못한 상호작용(경쟁 조건)도 없다.
2. **간섭이 없다**: “격리”가 “간섭”의 오기일 가능성. 한 스레드가 순차적으로 처리하므로 연결 간 간섭이 거의 없다.

어느 쪽이든 핵심은 “IO 멀티플렉싱은 한 스레드가 여러 연결을 같이 돌리므로, 공유 자료구조를 두 요청이 동시에 건드리는 일이 없다”는 것이다. 이것이 우리 프로젝트에서 `flight_store`의 좌석 배열을 `pthread_mutex`로 보호하면서도 연결 처리 자체는 스레드 경쟁 없이 돌리는 이유와 맞닿아 있다.

### 관련 정의 — 동시성

같은 주제에서 “동시성이란 여러 프로세스가 실행될 때 모두 같은 프로세스를 사용하더라도 모두 인터리빙하는 현상”이라고 한 부분. 이것도 오기로 보인다.

- “여러 프로세스가 실행될 때” → “여러 스레드(또는 여러 작업)가 실행될 때”가 맞다.
- 정정하면: **동시성은 여러 작업이 같은 시간대에 진행되는 현상이다. 같은 프로세스(메모리)를 공유하더라도 작업들이 인터리빙(번갈아 실행)한다.**
- 동시성이 꼭 여러 프로세스를 필요로 하지 않는다. 한 프로세스 안의 여러 스레드, 심지어 스레드 하나가 IO 멀티플렉싱으로 여러 연결을 번갈아 처리하는 경우도 동시성이다.
- 우리 서버는 `main.c`가 프로세스 1개를 만들고 `worker_pool_start()`가 스레드를 N개 띄운다. 즉 동시성을 “하나의 프로세스 + 여러 스레드”로 만든다. 강의의 정의가 틀린 게 아니라 대본의 “프로세스”가 “스레드”여야 한다.
- 동시성(concurrency)과 병렬성(parallelism)은 다르다. 병렬성은 여러 작업이 같은 순간에 실제로 실행되는 것(멀티코어 필요). 동시성은 겹치는 시간대에 진행되는 것(인터리빙 포함).
