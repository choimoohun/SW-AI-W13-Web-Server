# PR 리뷰 반영 루프

리뷰 코멘트를 그대로 믿고 고치지 않는다. 각 코멘트가 실제 코드에서 맞는 말인지
에이전트가 먼저 거꾸로 따라가 확인하고(triage), 사람이 반영할 것만 고르면(check),
그 항목만 고친다(apply). 단계 사이에는 반드시 사람이 있다.

```
fetch ─▶ triage(에이전트) ─▶ check(사람) ─▶ apply(에이전트) ─▶ 확인(사람)
                  ▲                                │
                  └──── 새 리뷰가 달리면 fetch부터 ◀┘
```

체크리스트 파일: `docs/records/pr_reviews/PR-<번호>.md`

## 0. 지키는 규칙

- 루트 `AGENTS.md`의 "하지 말 것"을 그대로 따른다. 요청 없이 커밋·푸시·PR 코멘트를 하지 않는다.
- 실행하지 않은 명령의 결과를 쓰지 않는다. "통과할 것" 대신 실제 출력의 요지를 적는다.
- 체크되지 않은 항목은 고치지 않는다. 고치다가 다른 곳도 고쳐야 할 것 같으면 고치지 말고 '결과'에 적는다.
- `docs/TEAM_RULES.md`, `docs/DECISIONS.md`와 부딪히는 제안은 판정을 '판단 보류'로 둔다. 확정된 결정을 리뷰 하나로 뒤집지 않는다.

## 1. fetch — 리뷰 모으기

PR이 여러 개면 **PR마다 파일을 따로** 만들고 따로 triage한다. 쌓인(stacked) PR이면
아래에 깔린 PR(base가 main 쪽인 것)부터 처리한다.

```sh
make pr-review PR=<번호>        # = python3 scripts/pr_review_fetch.py <번호>
```

이미 파일이 있으면 새 코멘트만 뒤에 붙는다. 사람이 적은 체크와 메모는 그대로 남는다.

## 2. triage — 항목마다 코드로 거꾸로 확인하기 (코드 수정 없음)

'(에이전트)' 칸이 빈 항목마다:

1. **위치 찾기 (두 군데)**: 리뷰는 PR 당시 커밋을 본 것이다. 두 곳을 모두 본다.
   - PR 당시: `git fetch origin pull/<번호>/head:pr-<번호>` 후 `git show pr-<번호>:<파일>`
   - 지금 작업 브랜치(예: `eungi-dev`): 같은 파일, 또는 함수 이름으로 `grep -n`
   지금 브랜치에서 이미 고쳐졌거나 없는 파일을 가리키다가 생겼으면 '작업 브랜치 상태'를 `이미 해결됨`으로 적고
   근거에 어느 커밋·파일에서 해결됐는지만 적은 뒤 다음 항목으로 넘어간다.
2. **주장 분해**: 코멘트가 말하는 것을 한 문장의 검증 가능한 주장으로 바꾼다.
   예: "proxy.c 178행의 RR 인덱스가 오버플로하면 음수 인덱스가 된다".
3. **거꾸로 따라가기**: 그 줄로 들어오는 호출 경로와 데이터를 따라가서 주장이 실제로 성립하는 조건을 찾는다.
   - 호출하는 쪽: `grep -n "함수명" src/*.c`
   - 관련 계약: `include/*.h` 주석, `docs/DESIGN.md`의 소유권·스레드 규칙
   - 동시성 주장이면 어느 스레드(워커 / 프록시 스레드)에서 도는지 먼저 확인한다.
4. **가능하면 재현**: 기존 테스트나 짧은 명령으로 실제로 보여 준다.
   - 단위: `make test`, `make test-flight`, `make test-tracking`
   - 통합: `make integration`, `make integration-req`, `make edge-cases`, `make review-cases`
   - 메모리·경쟁: `make asan`, `make tsan`, `make leak`
   재현하지 못했으면 "재현 안 함, 코드 근거만"이라고 쓴다.
5. **칸 채우기**:
   - 판정: 타당 / 부분 타당 / 해당 없음 / 판단 보류
   - 지금 작업 브랜치에서: 남아 있음 / 이미 해결됨 / 해당 코드 없음
   - 근거: 파일:줄과 따라간 경로를 2~4줄로. 재현했으면 명령과 결과 요지.
   - 제안 수정: 무엇을 어디서 바꿀지 한두 줄. 코드 전체를 쓰지 않는다.
   - 검증 명령: 고친 뒤 돌릴 `make` 타깃. 동작이 바뀌면 추가할 테스트 이름까지.
   - 위험도: 낮음(국소 수정) / 중간(여러 모듈) / 높음(스레드·소유권·프로토콜 변경)
   - 답글 초안: 리뷰어에게 보낼 한두 문장. 해당 없음이면 그 이유.
6. 같은 원인을 가리키는 항목은 첫 항목에 "R7과 같은 원인"처럼 묶어 적는다.

triage가 끝나면 **멈추고** 사람에게 요약을 보낸다: 항목 수, 판정별 개수, 위험도 높은 항목, 판단 보류 항목과 그 이유.

## 3. check — 사람이 고르기

사람이 파일을 열어 반영할 항목을 `- [x] 반영 승인`으로 바꾼다. 방향이 다르면 '메모(사람)'에 적는다.
에이전트는 이 단계에서 아무것도 하지 않는다.

## 4. apply — 체크된 항목만 고치기

사람이 "반영해줘"라고 하면 `[x]` 항목을 위험도 낮은 것부터 하나씩:

1. '메모(사람)'가 있으면 그 방향을 따른다.
2. 동작이 바뀌는 수정이면 **실패하는 테스트를 먼저** 추가하고 실패하는 것을 확인한다
   (`tests/unit/` 또는 `tests/integration/`). 문서·주석 수정이면 건너뛴다.
3. 고친다. 그 항목에 필요한 파일만 건드린다.
4. 그 항목의 검증 명령 + `make` + `make test`를 돌린다.
5. '결과(에이전트)'에 바꾼 파일, 돌린 명령, 결과 요지를 적는다.
   - 두 번 고쳐도 실패하면 되돌리고 "실패: 원인 추정"을 적은 뒤 다음 항목으로 간다.
6. 모든 항목이 끝나면 `make integration`을 한 번 더 돌린다.
7. `docs/records/VERIFICATION_LOG.md`에 "PR #<번호> 리뷰 반영" 항목으로 돌린 명령과 실제 결과를 남긴다.

끝나면 사람에게 보낸다: 반영한 항목, 실패·보류 항목, 돌린 명령과 결과, 커밋 메시지 초안.
커밋·푸시·PR 답글은 사람이 요청할 때만 한다.

## 5. 다시 돌기

리뷰어가 새 코멘트를 달면 1단계부터 다시 한다. 이미 있는 항목은 다시 만들지 않는다.
